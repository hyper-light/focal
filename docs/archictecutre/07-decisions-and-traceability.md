# Decisions, source conflicts, and traceability

Status: proposed Focal decisions. The user specified Rust; RAM-primary storage with disk durability; laptop through multi-region/Meta-scale ambition; and minimal incremental complexity through six deployment stages. These requirements govern the adaptation. Nothing here asserts implementation is already complete.

The frozen [reference snapshot](reference/README.md) preserves upstream accepted wording even when conflicting or superseded. [01](01-source-audit.md) records observed Sylk behavior and static concerns. [02](02-domain-and-lifecycle.md) records domain decisions D-01 through D-08; the F-series below records system decisions.

## 1. Source precedence

1. User requirements and explicit corrections in this task.
2. The reconciled numbered Focal documents as the proposed implementation baseline.
3. Later explicit Hecate amendments over earlier conflicting Hecate passages.
4. Sylk source and tests as evidence of existing behavior and lessons, not automatic target semantics.
5. Historical bug reports as regression scenarios, not proof the current Sylk revision still has the bug.

Where Focal improves an underspecified algorithm, the improvement is labeled a design decision. A citation to Hecate does not validate pseudocode under arbitrary schedules or crashes.

| F36 | Clients are routed by the directory through a per-node cache fed by bounded partition route-change logs, and redirected by the data service before any replica sees a misdirected request; nodes address replicas directly | A stale client must learn where its ledger's log leads without a fleet-wide subscription or a poll of every partition: the partition already commits every route change, so a bounded log per partition plus a cache that pulls exactly what it watches keeps routing knowledge bounded and consistent, while the replica's own leader (consensus state) stays the truth a follower redirects to. Node-to-node traffic is never routed this way, because a heartbeat delayed by a directory lookup costs a quorum ([24](24-placement-execution-and-fleet-control.md) §14) | [24](24-placement-execution-and-fleet-control.md) §14, P08, P09 |
| F33 | A node's directory identity is its enrolled key, and a credential is renewed under that key with the replaced certificate retired after a bounded grace | Binding proofs and grants to a certificate fingerprint would make every renewal a re-enrollment with a new generation, invalidating group grants and placement progress; binding them to the key the authorized certificate carries lets a renewal change nothing in the directory. The registry keeps the replaced certificate authorizing for the sponsor's grace so work in flight completes and a holder that crashed before installing the renewal can still reconnect and converge on the committed one ([24](24-placement-execution-and-fleet-control.md) §11); the transport keeps authenticating by certificate fingerprint and learns the new one when the node presents it | [24](24-placement-execution-and-fleet-control.md) §11, P07, P09 |
| F32 | Disk is admitted through one shared envelope per volume that lives in `focal-memory`, and a tenant is admitted to a node when a committed placement first assigns it a session | Every durable owner (log writer, content store, checkpoint path) must refuse before it acknowledges, and they sit below any archive crate in the dependency graph, so the envelope lives beside the memory budget in `focal-memory` rather than in the planned archive crate; its counters are shared by owners on different threads, the one boundary [10](10-ownership-and-failure-policy.md) already justifies for the memory budget. Tenants are not configured per node: the placement that assigns a tenant's session is the admission request, answered under `node.max_tenants` and the node budget, and a node that cannot fund the tenant records a capacity refusal against its own assignment instead of hosting it unfunded ([24](24-placement-execution-and-fleet-control.md) §10) | [24](24-placement-execution-and-fleet-control.md) §10, [04](04-storage-and-distribution.md) §5, P09 |
| F31 | Placement progress is committed directory state derived from signed readiness, and the pre-release control-plane formats advance rather than fork | A controller that kept assignment progress in memory would lose it at every leader change and could not be inspected; the partition now records one monotone progress row per copy, bounded refusals, the copies an activation leaves behind and a measured guarantee report ([24](24-placement-execution-and-fleet-control.md)). Custody and promotion are never asserted by the controller: readiness signed by the copy itself raises a row to `CustodyVerified`, and the cutover fence is recorded only once every voter is promoted. The partition checkpoint becomes schema 2 (schema 1 restores through a typed conversion that invents no custody), the control checkpoint schema 4 and the command envelope schema 2; none of these formats shipped, and a partition group bootstrapped at schema 1 is not the same group at schema 2 | [24](24-placement-execution-and-fleet-control.md), [04](04-storage-and-distribution.md) §13, P10 |
| F30 | The peer verbs are authored shapes of `claim.submit`, and corrections and follow-ups derive every identity from the facts they rest on | A second workflow engine for challenges would duplicate admission, journaling and recovery; instead `claim.challenge`, `claim.consult`, `claim.correct` and `claim.follow_up` are typed documents lowered to one claim document before the shared compiler runs, so they share the frame, the `n1:` identity, the receipt and the coverage table row of `claim.submit`. A correction's and a follow-up's occurrence, claim, validation and timer identities are keyed BLAKE3 digests of the ledger, the author and the followed claim, verdict and text, so identical facts yield byte-identical descriptors and the owner's content identity resolves a repeated delivery to one committed claim without a reservation step. `claim.lineage` and the native `claim.wait` are client-composed bounded reads over the existing wire, not new owner reads. | [19](19-cli-mcp-implementation.md), [21](21-native-input-format.md), P17, P19, P20 |
| F29 | Peer follow-ups relate to the claim they follow; they never reopen it | A challenge whose verdict failed and a consultation that was answered are terminal, and a terminal or released claim cannot own a child (P17.12), so a correction and a follow-up consultation are ordinary authored claims linked by `invalidates` and `refines` to the claim they follow, under whatever enclosing cause their author holds. The owner gates them by that claim's authored policy (`corrective_allowed`, `escalation`, `single_issuer`, `max_follow_ups`) and, for a correction, by the exact report of the terminal negative verdict at the challenge's current registration generation, cited as `reviews` evidence; the relation index makes both listable and bounds the single-issuer and follow-up counts. `caused_by` keeps its live-parent ownership meaning, with the same escalation vocabulary deciding who besides the issuer may cite a parent. | [21](21-native-input-format.md), [17](17-lifecycle-state-and-authority.md), P16, P17 |
| F28 | Peer follow-up policy and exact evidence are authored claim content, not a separate policy artifact | A challenge's or consultation's follow-up rules must be immutable, hashed with the claim and readable by every owner without a second lookup; the plan's `peer-policy` artifact would need standalone artifact registration the native engine does not offer and a second admission read. Descriptor schema 2 therefore carries an optional `PeerPolicy` (`corrective_allowed`, `max_follow_ups`, `single_issuer`, `escalation` none/holder/evaluator) after the deadline, and `reviews`/`derived_from` relations may target exact evidence (`RelationTarget::Evidence(ArtifactRef)`, input tag 4, canonical tag 5), admitted only when that artifact is committed at that descriptor hash. Schema-1 identities, bytes and hashes are untouched; the V1 codec refuses the new target; `ByRelation` indexes evidence targets by artifact identity so corrections and reviews of one artifact are listable. | [21](21-native-input-format.md), [22](22-native-record-format.md), P16, P20 |
| F27 | Managed generations are bounded by ordinal count and recycled under one slot-generation watermark | A principal's request stream must stay finite on both sides without time-based deletion: a generation issues at most its rotation bound of ordinals, and once every ordinal through the bound is retired the client stops issuance durably, closes exactly, records the retired fence, removes the old store and registers again above the generation the slot presents. The registry evicts only vacant pairs, the longest-closed first, and presents `max(last generation, watermark)` on every vacant pair so a registration is assigned exactly one above what it cited (the frozen client rule) while still lying above every generation the registry ever issued; the watermark is persisted in `FOCALSS7` and derived from the retained pairs of an SS6 checkpoint. Occupancy reads answer only for the authenticated principal's own pairs. The rotation bound is part of the coordinator record; campaigns lower it with `FOCAL_MANAGED_ROTATION`. | [15](15-managed-request-streams.md), [13](13-cli-and-agent-implementation-plan.md), P17 |
| F24 | Native index families are ordinary recorded rows, funded per operation and rederived by every reader | Bounded lists need ordered key ranges per predicate. The thirteen families ([22 §7](22-native-record-format.md)) are unit rows of the same range: derived from the exact primary rows the leader writes, required exactly by replay validation, rederived by checkpoint validation and written by the import image, so no reader trusts an index it did not check. Index rows count toward the batch and toward every completion and respondent promise; a promised artifact's inputs are bounded by `NativeLimits::artifact_inputs` and narrowed by a small batch instead of refusing every report; the range envelope prices deletions by declared heap (`deleted_heap`) so an index deletion is not priced as the largest entry; the standard record envelope grows to 6 MiB to hold a preparation-sized body plus every fixed row. Only `ByStatus` changes after creation; artifacts, definitions and testaments carry no creation row. Lists are stateless with node-authenticated continuations that name the last visited row. | [22](22-native-record-format.md), [19](19-cli-mcp-implementation.md), P03, P07, P18 |
| F23 | One native driver for every host, one journal per adapter, and explicit consumption of MCP results | The CLI and the MCP adapter share `focal-native-client`'s driver (resolve, compile, encode, fingerprint, journal, drive) with only the blocking read and cancellation supplied by the host, so identical documents yield byte-identical frames and one fix serves both. Each adapter owns its `n1:` journal (`client/native`, `client/mcp-native`) as the V1 request stores do, so neither can consume the other's identities; cross-adapter observation is the owner's outcome read by request key, not a shared file. MCP results stay listed until acknowledged because a tool reply can be lost between the adapter and the agent; the CLI marks delivery on a successful print because its reader is the process that printed. The engine probe runs on the worker runtime before the catalogue is built. | [19](19-cli-mcp-implementation.md), P17 |

## 3. Reconciled Hecate gaps and contradictions

| Source issue | Why it cannot be copied literally | Focal resolution |
|---|---|---|
| LEDGER §3 happy-path status list omits failures required by LEDGER_CORE §4 | No exhaustive reducer or wire enum can be built from it | [02](02-domain-and-lifecycle.md) defines complete active/terminal vocabulary, transition table and refusal cases |
| LEDGER §4 describes incremental SCC machinery; LEDGER_CORE §3 explicitly rejects a global SCC monitor | Conflicting monitor ownership/algorithm | Per-parked-scope closures with SCC condensation and independent brute-force oracle |
| Rank refers to `invalidates` while LEDGER relation enumeration omits it | Security classification cannot match an unregistered string | Closed `Invalidates` variant plus exhaustive override classification |
| Earlier protocol ADR text refers to TCP; later PROTOCOL mandates QUIC | Different wire assumptions | Focal authenticated framed QUIC; no claim of Hecate byte compatibility |
| STORE generic data shard has its own log; claims-specific clauses retain one session log | Applying generic sharding to claims destroys the chosen session order | Claims partitions consume one session log; directory/metadata groups have separate authority |
| MATERIALIZER §5 mentions HRW while later STORE requires one range directory | Two independent splitters create mismatched ownership | One range map for authoritative state/apply; cache placement is separate and nonauthoritative |
| MATERIALIZER conflict detection depends on overlay observations while workers race | Smaller-index writers may not have executed yet; stale reads can evade a local check | Complete tracked access audit at deterministic barrier; recompute speculative suffix/epoch |
| MATERIALIZER read+write DAG example can add self-edges | Read-modify-write can deadlock its own node | Exclude self-edges, deduplicate predecessors, test RMW explicitly |
| Max-writer-index overlay drops earlier versions | Earlier log entries may need earlier values; write-write resolution alone does not fix read dependencies | Per-entry writes/multiversion overlay plus serial-order validation |
| Deferred entry with already computed successors | Successors may contain stale dependent computations | Discard and recompute all affected results, including indirect dependencies |
| Epoch size derived from local timing but claimed replay deterministic | Replica measurements can disagree | Version sizing inputs or prove epoch selection cannot affect state/delta outcome |
| Cross-node apply called “no 2PC” without visibility protocol | Common order does not prevent torn reads or partial apply after crash | Deterministic participant batches, recovery replay, fixed-prefix publication barrier |
| Split described as seed/tail/directory CAS | Source may keep accepting work after destination cutoff | Logged stop/activation barrier and epoch fencing before directory publication |
| Watch no-gap/no-duplicate language conflates transport and effects | Lost acknowledgements cause replay; unrelated sequence clocks are not comparable | Session sequence + ordinal cursors, explicit redelivery/Resync, idempotent consumer effects |
| “Read-your-watch” assumes current read barrier is at least received delta | Client may route to a lagged/moved reader | Carry minimum sequence across retries and wait for the requested publication prefix |
| “Small” sequencer lifecycle projection | Its size can grow with a large live session | Measure and budget projection; asynchronous versioned proofs for nonlocal admission; declare ceiling |
| Monitor closure budget “alarms” after breach | Alarm alone does not bound allocation | Reserve before registration; reject/pressure before unsafe growth |
| Idle-time or unspecified retirement cadence | Saturated systems might never reclaim | Paced debt-based custody/retirement with reserved control capacity |
| Durable log but artifact replicas not in failure contract | Committed proof could reference unavailable/lost evidence after region loss | Verify evidence custody under the same promised failure set before close |
| Minimum/maximum watermarks across different clocks | Per-shard indexes and physical offsets cannot be compared directly | Typed clock domains and explicit mapping; common session prefix for graph visibility |

The amended algorithm is motivated by the references, not a claim to have implemented Calvin or reproduced a paper's throughput. Deterministic sequencing and declared-access execution have precedent in [Calvin](https://www.cs.yale.edu/homes/thomson/publications/calvin-sigmod12.pdf); Focal's precise retry, memory and publication rules remain obligations of its own implementation.

No missing deployment size justifies stopping the implementation plan. Defaults cover local use; users provide additional intent only when the next use case requires it. Scale and safety claims must follow measurements and active placement state.

The [2026-09-05 CLI research](11-cli-spec-research.md) and [agent workflow audit](12-agent-tools-and-workflows.md) add explicit Focal choices. `--target` means subject and `--source` means issuer, with singular filtered reads rejecting ambiguity. They are not endpoint selectors. The user's challenge proof and consult work-quality requirements supersede weaker receipt-only source defaults. Corrective issuance remains an authorized, durable workflow with evidence; consultation normally produces targeted follow-up work. Hecate's later accepted `SKILLS_API` amendment treats optional TS/Python bindings as authoring-time document generators, so a Rust CLI/MCP/skill interface does not require an embedded script runtime. P17–P20 implement these choices without changing earlier persisted command ordinals or admitting caller-supplied lifecycle authority.
