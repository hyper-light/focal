# Ownership and failure policy

Production Rust must not panic. Tests may use assertions, unwraps, and panics. Prefer owned values, borrowing, and moving values between owners. Use `Arc` only where simultaneous owners on different threads actually need the same state, or a dependency requires it. Moving a value to one thread does not justify shared ownership.

These requirements apply to the laptop implementation and every distributed deployment step. Adding peers or regions does not relax them or introduce an operator configuration switch.

## Error handling and enforcement

The workspace denies explicit panic, unwrap, expect, unreachable, TODO, and unimplemented paths. It also denies dynamic indexing/slicing and unchecked arithmetic, including debug builds. `clippy.toml` disallows assertions and convenience output macros in production: even `println!` can panic when stdout is closed. Use fallible I/O and propagate errors, or explicitly discard a diagnostic write error when there is no recovery action.

`bash scripts/check-production.sh` compiles libraries and binaries without test configuration and denies these lints on the command line. Do not add production allowances for them. The separate all-target Clippy invocation covers test code; test-only allowances permit test assertions without weakening the production pass. Both are CI gates. The contract checker requires every crate to inherit workspace lints. These use `deny`, because dependency derive macros contain broad lint allowances that conflict with command-line `forbid` even when they emit no offending code.

Lint success is a guardrail, not a proof that arbitrary dependency calls cannot panic. Review runtime creation, clocks, collection capacity, conversions, serializers, parsers, callback execution, destructors, and dependency preconditions. For example, the executable constructs Tokio through its fallible builder instead of using a macro that unwraps initialization. Timeouts use checked deadlines. Canonical encoding returns `CanonicalError` when a length or allocation cannot be represented; valid v1 encodings and hashes stay unchanged.

Return a typed capacity, invalid input, stale handle, corruption, or unavailable error as appropriate. Check admission and deadline failures before proposing a mutation. An internal accounting inconsistency must not silently mint capacity or return a successful partial result. Saturating arithmetic is appropriate for an explicitly saturating telemetry counter, not for sequence numbers, durable offsets, epochs, or resource charges. A persistence or consensus invariant failure stops the affected owner from acknowledging later work. Unknown commitment still requires a same-key retry; it must not be presented as a definite rejection.

The Raft adapter contains upstream unwinding panics at construction and mutable dependency entry points, permanently fails that in-memory owner, and requires disk recovery before reuse. Runtime executor unwinds produce an error for read-only work; effectful reconciliation remains indeterminate until its external outcome is known. The executable also contains Tokio builder unwinds: that dependency can panic on OS worker exhaustion even though its builder returns a `Result`. Shutdown sends use nonblocking admission, and asynchronous owner joining uses a fallible standard-library thread builder. Containment is a boundary for dependency failures, not permission to add panics to Focal. Rust's panic hook may still report a caught dependency panic. Process aborts, allocator exhaustion that aborts, and nonreturning callbacks cannot be recovered by `catch_unwind`; bounded admission and process supervision remain necessary. General-purpose collection allocation and dependency internals are not formally proven panic-free by these checks.

## Ownership choices implemented in the cleanup

- Node and enrollment host handles own cloneable channel handles. Servers accept owned cloneable handlers; callers no longer have to allocate an `Arc<dyn Handler>`. The local executable borrows its server future during shutdown. The shared-port listener builds its TLS identity and verifier once and applies the common transport policy without allocating and discarding duplicate shared configuration or private-key copies.
- Local and fleet mutation dispatch borrow the admitted peer and request, then move the command into authentication. They retain only the reply header instead of cloning the full request. Receipt preflight still requires a command copy; removing it requires a borrowed authentication/hash interface with the same authorization checks.
- Grouped session owners retain exact Ready/LightReady work across disk admission and completion. They poll the physical writer without moving blocked inputs into another queue. A stop intent bypasses blocked scheduling without mutating Raft and has a bounded unknown-outcome deadline.
- A worker owns its task and budget allocation until the completion is consumed or dropped. Each fixed worker has its own receiver. The owner keeps separately charged assignment metadata; it does not share whole tasks or serialize worker receives behind a mutex.
- Prepared directory, cursor, and range metadata own their candidate state. Checked owner identity plus revision validates publication. Enrollment preparation uses a private fresh identity. These provenance checks do not allocate an `Arc<()>` marker.
- Normal stream deliveries own their allocation. A single reserved control slot retains a shared permit so an outstanding delivery cannot release or duplicate the slot's accounting.
- Local, replica, control and content handlers move response allowances through their queues and `OwnedResponse` into Unix/QUIC delivery. An unconsumed oneshot is still resident memory. QUIC retains the allowance until acknowledgment or cancellation under the existing deadline; cancellation resets buffered output before releasing it. Receipt preflight misses retain their request allowance until evidence admission.
- Membership replies own their allowance through caller consumption. Request and read-context buffers are dropped before transferring that allowance, and empty pending-queue backing is released while the final permit is still held. A successful membership result requires both committed application and a later current-term quorum read; a leadership-transfer acknowledgment reports initiation only.
- Content manifests validate sequence counts against the encoded remainder before allocating. Upload preferences govern new local uploads; immutable format limits govern imports and reads, including after recovery. The bounded content actor and coordinator own transfers and borrowed peer-pool operations without additional `Arc` wrappers.

## Remaining shared ownership

Each new `Arc` needs a concrete lifetime/concurrency reason near its definition and a test of the relevant boundary. Do not replace an unnecessary `Arc` mechanically with `Rc`: first determine whether ordinary ownership or borrowing removes the allocation entirely.

| Boundary | Why state is shared |
|---|---|
| Memory snapshot roots, COW pages, immutable content, lease clocks and lease accounting | Detached readers retain an old view while the owner publishes a new view; shared content and charges live until the last reader releases them. Concurrent snapshot tests exercise this. |
| Memory budget counters | Owned permits may be released by workers and response tasks after the admitting owner has moved on or stopped. Immutable parent links enforce session, tenant and node limits together; each permit follows those links without allocating a separate parent-permit chain. |
| Scheduler dispatch lease | A detached worker owns dispatch while the scheduler weakly observes liveness for completion accounting and active-ID deduplication. |
| Stream control permit | The subscription and its one outstanding control delivery share the reserved capacity; a second control delivery is refused until the first is released. |
| Shared physical WAL | Independent session and control owners enqueue to one bounded disk writer. Its last handle closes and joins that owner. A grouped fleet retains each physical writer until all logical sessions stop, preventing session removal from joining disk IO on a live session worker. Ambiguous persistence stops subsequent acknowledgments. |
| Grouped replica channel backing | Host clones, the node worker and the outbound receiver can outlive each other on different threads. One shared allocation guard keeps their channel and handle backing charged until the last releases it. Requests and session state remain individually owned. |
| Runtime executor, immutable catalog, clock, cancellation, and content reader | Fixed worker threads use these concurrently; cancellation crosses owner/worker boundaries, and content readers coordinate with upload writers. |
| Transport authentication grants and peer cache/admission state | Concurrent requests must observe the same revocations, connection cache, and in-flight capacity. The replication driver borrows its peer pool for a bounded set of concurrent sends. |
| Quinn/rustls configuration | Their public APIs require reference-counted immutable configuration shared by connection tasks. |

Budget retention and publication tests must cover drop order, owner shutdown, stale prepared handles, and readers surviving publication. Performance claims require measurements: this cleanup reduces unnecessary allocations and reference-count operations, but does not establish throughput or multi-region scale. The [implementation status](09-implementation-status.md) records remaining qualification work.
