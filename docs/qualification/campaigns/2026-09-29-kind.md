### Defect D1 (manifest) — the rendered kustomization creates no Namespace

> **Resolved 2026-09-29:** the renderer emits `namespace.yaml` first; goldens and the render test follow.
`deploy/kubernetes/kustomization.yaml` sets `namespace: focal` and every object
carries `namespace: focal`, but no `Namespace` object is rendered, and the
renderer's own apply note (`crates/focal-node/src/deployment/render/kubernetes.rs:331`:
"`kubectl apply -k .` applies everything") assumes it exists. On a fresh cluster:
```

Error from server (NotFound): error when creating "deploy/kubernetes": namespaces "focal" not found   (×7)
```
Root cause: `render::kubernetes` emits the namespace only as a field on each
object and on the kustomization, never as a resource. Fix belongs in the renderer
(emit `namespace.yaml`, list it first in `kustomization.yaml`) or its note/docs
(`kubectl create namespace focal` first). Remedy here (tracked tree untouched):
overlay `$KD/overlay/` = `namespace.yaml` + the tracked base, applied with
`kubectl kustomize --load-restrictor LoadRestrictionsNone $KD/overlay | kubectl apply -f -`

### Defect D2 (focal, headline) — native activation before scale-out fail-closes the later-added voters

> **Resolved 2026-09-29 (doc 09):** reproduced in process; the cause was not the
> decoder floor but `apply_activation` comparing the record's configuration hash
> with the consensus's *current* configuration, which on a late copy already held
> the learner's own addition committed after the record. The apply compares the
> record's configuration index alone now. The analysis below is kept as written.
**Reproduction (run 1 order):** founder Ready → `activate native`
(founder, single session voter) → hosts enrolled and joined → `apply deployment`
(target.yaml: survive zone, max_failures 1 → adds focal-b and focal-c as session
voters). As soon as apply promoted the two hosts, **both host replicas stopped**:
```
focal: session <SESSION> stopped: persisted ledger identity, format or prefix mismatch
```
(`LedgerError::Corrupt`, fail-closed). The session never became authoritative on
the hosts: placement stuck in `phase: Catchup`, `blocked_by:
["Assignment(CaughtUp) on <founder>", "Assignment(Installed) on <b>",
"Assignment(Installed) on <c>"]`, `achieved_max_failures` stayed 0, the
founder's `readiness.policy_satisfied` went false — and it never healed. The pods
stayed **Ready** the whole time (the `alive` probe is only "the process answers
its identity", `cluster_admin.rs:1065`), so Kubernetes never restarted them: a
silent, self-inflicted degradation.

Root cause: the founder committed the `FOCALAC1` native-activation record
(Genesis, over an empty legacy prefix) while it was the session's only voter.
When `apply deployment` later added focal-b/focal-c, each opened a fresh copy
(`open_copy` → `NodeConfig::joining`, bootstrap voters = the single founder) and
replayed the founder's log, which contains that activation entry. Applying it
(`native_hosting.rs::apply_activation`) requires the copy's successor **decoder
floor to already be durable** (`if !self.consensus.decoder_floor_ready(native_format_hash())
{ return Err(Corrupt) }`). A voter added *after* activation over an empty prefix
never went through the pre-activation native-promise handshake
(`begin_native_support`, driven by the leader's `ManagedSupport` probe of a
*prospective* learner, `fleet.rs:2112`), so it replays a native activation it
never promised for and fails closed. `docs/cluster-admin.md` states the intended
invariant — activation "proposes the committed native activation *once every
voter has promised the native decoder*" — which holds only if every voter is
present *before* activation; there is no path that re-drives the promise for a
voter added afterwards over an empty prefix, so the group cannot recover. Not a
manifest issue and not fixed here (task: reproduce and stop). Suggested fix
direction: either drive the native-support promise as part of admitting a new
voter to an already-native empty-prefix session, or refuse to promote a voter
that has not recorded the successor floor (so the guarantee stays honestly
unsatisfied instead of a fail-closed stop).

**Working order (run 2):** redeploy fresh → founder Ready → invitations → hosts
join → **`apply deployment` first** (session settles with 3 voters, achieved
Zone/1) → **then `activate native`**. All three replicas
activated cleanly: `native_active=true` on founder, focal-b, focal-c;
`applied=committed` equal on all three; **no** "stopped" lines; standing profile
`AuthoredV1`; `achieved_survive=Zone`, `achieved_max_failures=1`, `blocked_by=[]`.
The rest of the campaign ran on this healthy tree.

### Defect D3 (minor) — first activate-native returns a transient `unavailable`
On each run the *first* `activate native` returned
`[unavailable] metadata owner is unavailable` (exit 6); an immediate retry
succeeded. The command is idempotent so this is only a cosmetic first-call race
against owner readiness, but a freshly-Ready founder should not need a retry.

> **Resolved 2026-09-29 (doc 09):** not a race with readiness — the first
> activation itself starts the durable promise of the native decoder and was
> answered `PersistencePending` for the write it had just staged, which the
> admin protocol worded `unavailable`. The owner holds an activation until its
> barrier holds now (`activation_gate`), charged to the request time; on a
> real process the first online call activates (`tests/online_activation.rs`).

### Defect D4 (focal) — follower operator read hangs ~30 s then returns `unavailable`

> **Resolved 2026-09-29 (doc 09):** followers serve linearizable reads through Raft's ReadIndex (barrier parked until applied, page from the copy's committed core); on real processes each read through a host answers in ~45 ms.
A domain read (`get claim/artifact/testament`) issued on a host's local operator
socket while that host is a session **follower** blocks for ~30 s and returns
`unavailable` instead of forwarding to the leader or failing fast. Reproduced on
both focal-b and focal-c (6/6 reads, 30.08–30.15 s each). Expected: forward to
the authoritative leader, or refuse immediately with the known leader named (as
`inspect cluster` does: `[not_leader] … (known leader: …)`). Operators reading a
replica directly hit a 30 s stall per call.

### Defect D5 (design/scale note) — metadata plane does not survive a founder loss
The rendered deployment + `apply deployment` gives the **session (data)** group
zone survival (3 voters across zones) but leaves the **root metadata group
single-voter** (`voters=[founder]`, focal-b/focal-c remain learners). So
metadata/placement/membership operations do not survive a founder loss until the
founder pod restarts (shown in (b): `root_leader=not_leader` during founder-down).
Promoting the hosts to root voters (`promote learner --node`) is a
separate step that neither `apply deployment` nor the deployment docs mention for
zone survival. The founder PDB (`maxUnavailable: 0`) is consistent with this
single-founder metadata design, but an operator asking for "survive zone,
max_failures 1" would reasonably expect the control plane to survive one zone
loss too. Worth deciding whether zone survival should also expand the root group,
or whether the docs should state the metadata plane's single-founder limit and
the manual promote step.
