# Performance record — 2026-09-29, macOS arm64 (after allocation audit R5)

Host: Apple M5 Max (arm64), macOS 26.4.1, 128 GiB, page size 16,384 bytes
(`getconf PAGESIZE`). Build: `bench` profile
(`cargo bench`, release codegen). Same host class and the same benches as
[2026-09-12](2026-09-12-macos-arm64.md); the machine was not quiet (a second
session's build ran beside these), so the numbers are a bound on the gain, not a
floor. Only the paths R5 changed are recorded here; the rest of the 2026-09-12
record stands.

## What changed

Allocation audit R5 (`docs/qualification/allocations-2026-09-29.md` §6): byte
payloads serialized as bytes, not sequences. postcard writes `serialize_bytes`
and a `Vec<u8>` sequence identically (varint(len) ‖ bytes), so no wire or
durable byte changed (`focal_memory::serde_bytes`, proved across the varint
boundaries); a decode takes the bytes in one exact, fallible reservation
instead of a per-byte visitor, and every size pass over a payload is O(1).

## Request codec (`focal-wire`)

`cargo bench -p focal-wire --bench codec`, 2 M iterations at 0 B and 256 B,
400 k at 4 KiB, 30 769 at 64 KiB.

| Case | 2026-09-12 ns/op | 2026-09-29 ns/op | MiB/s now |
|---|---|---|---|
| encode native, 0 B frame (53 B wire) | 45.2 | 34.4 | 1470 |
| decode native, 0 B frame | 38.5 | 38.7 | 1308 |
| encode native, 256 B frame | 64.0 | 44.2 | 6683 |
| decode native, 256 B frame | 164.7 | 54.9 | 5382 |
| encode native, 4 KiB frame | 261.7 | 120.4 | 32866 |
| decode native, 4 KiB frame | 1964.0 | 101.6 | 38972 |
| encode native, 64 KiB frame | 3040.3 | 1072.3 | 58335 |
| decode native, 64 KiB frame | 30694.6 | 776.0 | 80606 |

Reading: the per-request fixed cost is unchanged (~35–39 ns each way); decode
is a memcpy now (19× at 4 KiB, 40× at 64 KiB), and encode, whose size passes
were per-byte too, 2.2–2.8× at the larger frames. The 2026-09-12 reading that
decode "is copy-bound at ~2 GiB/s" no longer holds: it runs at the memory
copy rate, and the reason to move large payloads by reference is now only the
copy itself.

## Wire codec allocations (`focal-wire`, `benches/allocs`)

Unchanged in count — one exact allocation per encode and per decode, no
reallocations — as the audit predicted; the decode's allocation is now the
exact `visit_bytes` reservation at the frame's length.

## Durable WAL append (`focal-log`, `benches/allocs`, path A `Wal::append`)

The record's payload bytes were serialized per byte through every size pass and
into the frame; per append (20 appends per configuration):

| path | reallocs/append before → after | bytes/append before → after |
|---|---|---|
| batch=1, 64 B | 8 → 7 | 682 → 574 |
| batch=16, 64 B | 68 → 52 | 4,762 → 3,046 |
| batch=256, 64 B | 1,028 → 772 | 70,042 → 42,650 |
| batch=1, 4 KiB | 14 → 7 | 16,810 → 4,607 |
| batch=16, 4 KiB | 164 → 52 | 262,810 → 67,574 |

Allocations per append are unchanged (5 for a single record; 1.02–1.25 per
record in a batch); the reallocations that remain are the per-record frame
buffers and the batch vectors, which R6 (one buffer per batch, one write)
removes.
