# The adversarial battery: threats and their cases

Terminating condition 6 asks for one adversarial battery, covering decompression and size bombs,
tampering, misuse and protocol abuse, that runs every case together beside a threat-model
coverage table. This is that table, and `scripts/adversarial_battery.py` is the battery:

    python3 scripts/adversarial_battery.py run     # every case below, run together
    python3 scripts/adversarial_battery.py check   # the table against the source (in check-contracts)

`run` takes the test executables the workspace build made (`cargo test --workspace --locked
--no-run`, the build CI's Tests step makes) and runs each once with its cases as filters, in its
package's directory. Every case must match exactly one test and every one must pass; it prints this
table with each threat's cases passed. CI runs it on Linux and macOS after the workspace's tests
(`.github/workflows/ci.yml`, "Adversarial battery"). `check` needs no build:
`scripts/check-contracts.py` runs it, so a case renamed or removed fails the contracts before any
test runs, as does a threat with no case or a class of the condition with no threat.

## Who attacks, and where

- **A peer node** reaching a node's listener over QUIC: before its handshake completes (anyone who
  can reach the port), and after it, with a node certificate the cluster issued.
- **A participant**, an enrolled client, sending requests over QUIC within its grant, or over a
  node's local socket.
- **An agent** driving focal through the MCP adapter (JSON-RPC on stdio) or code mode (programs
  focal runs for it).
- **An operator's inputs**: configuration and policy files, deployment plans, invitations, key
  files, backups.
- **Whoever can write a node's or a client's disk**: what focal keeps at rest, sealed or not.

The table names, for each threat, the surface it reaches, the attack, the defense focal holds and
the tests that show the defense. A threat is covered only by tests that drive the attack itself:
the oversized header, the flipped bit, the revoked grant, the program past its heap.

## What is outside it

- The vendored `hyper-*` crates' own suites (the QUIC stack, the log, the TLS stack) run in their
  repository. This table covers what focal's code does with them: which TLS configurations it
  builds, what its frames, records and seals refuse.
- A node whose own credentials are stolen acts as that node within its grant. Credentials expire,
  are revoked and renew only with the holder's key (MU-2), and their custody at rest is condition
  5's.
- Volumetric flooding below QUIC is the host's and the network's to absorb. What reaches focal is
  bounded by what a listener's budget funds (PA-4).

## Found while building it

- **focal decompressed peers' certificates.** The record of 2026-10-05 said focal compresses
  nothing, and no compression crate was in the dependency inventory then. Since then the TLS stack
  (`hyper-tls`, vendored) has brought RFC 8879 certificate compression with brotli and zlib, on by
  default: a peer's compressed chain was decompressed during the handshake, before the chain was
  verified, into the length the peer declared (at most 64 KiB, which the stack checks first).
  `ServerTls` and `ClientTls` now take no certificate compression either way, every TLS
  configuration focal's endpoints hold passes through them, and a contract rule refuses a new
  place that builds one until it is seen to (DB-1). The decompressors the binary links are the
  TLS stack's alone, and a test of the resolved dependency graph fails if another comes in (DB-2).

## A case

A case is written `package:target:filter`: a workspace package, one of its test targets (`lib`,
`bin=NAME` or `test=NAME`) and a libtest filter naming one test of that target, its function name,
or a path suffix such as `tests::name` where the name alone is not unique. `check` finds the test
function in the files its target's root reaches through `mod` declarations; `run` requires the
filter to match exactly one test when the target's executable runs.
