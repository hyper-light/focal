# Focal comprehensive codebase audit — 2026-09-29

**Verdict:** Focal has a substantial protocol, persistence implementation, and adversarial test suite. It also has reproducible availability and recovery defects, a native client that runs out of capacity after ordinary cumulative use, and several architectural ceilings that prevent the current implementation from meeting its global-scale objective. Passing formatting, Clippy, dependency checks, and most integration tests does not close these issues. Fix the concrete failure paths first; qualify capacity and failure recovery before making stronger operating guarantees.

This audit covers the product as a whole: domain semantics, native and legacy engines, evidence, storage, Raft, ranges, routing, admission, clients, CLI, MCP, participant runtime, enrollment, deployment, observability, release tooling, and verification. Raft and global scale receive additional depth, rather than displacing the other areas.

**Initial audit: 35 finding records, originally 15 P1, 17 P2, and 3 P3.** These are dated evidence, not a claim that every original finding remains open after concurrent fixes. Section 14 extends the review of QUIC, Raft, allocation/reallocation, page faults, recovery, and very poor networks, and refreshes the status of earlier observations. Same-configuration recovery, native retry-journal lifecycle/races, byte-funded ingress, and post-revocation dispatch remain immediate priorities. Continuous operation additionally needs founder renewal and historical-state reclamation; global operation needs bounded delegated cells and component-level availability guarantees.

## 2. What the product actually does

Focal is an **agent coordination protocol and evidence ledger**. A claimant directs work to a respondent and declares what acceptance requires. A receipt establishes responsibility or delivery; it does not establish correctness. The respondent performs work outside Focal, attaches immutable evidence, and supplies a testament, including diagnostic evidence when work fails. The designated evaluator records results against the exact evidence and declaration. Satisfaction is derived from those committed facts. Native claims, artifacts, validations, evaluations, receipts, testaments, scopes, and monitors have distinct lifecycles; terminal state and release are separate facts.

The service does not execute arbitrary agent tools. `focal-runtime` is an optional participant-side embedding for handlers, with retry and reconciliation contracts. Treating its absence from a daemon execution path as a missing scheduler would misunderstand the product.

One binary supplies the service, CLI, and stdio MCP adapter. Local operation uses credentialed local IPC and a private data directory. Remote operation uses enrolled identities, authenticated QUIC, committed topology and placement, and independent session logs. Raft establishes ordering and durability; native records materialize deterministic committed state. Reads establish a quorum boundary or use explicit prefix/lease semantics. Content custody is separate from WAL durability: storing a reference in a replicated log does not make the referenced evidence durable on the promised fault domains.

The intended global architecture is **many independently ordered session ledgers**, partitioned discovery and placement, and geographically bounded operating units. Range materializers can spread a large ledger's state and verification work; they do not eliminate its single sequencing order. One laptop should preserve the same protocol semantics with a smaller physical topology and a weaker explicitly reported durability guarantee.

Relevant contracts include [domain and lifecycle](../archictecutre/02-domain-and-lifecycle.md), [storage and distribution](../archictecutre/04-storage-and-distribution.md), [native lifecycle storage](../archictecutre/18-lifecycle-storage-upgrade.md), [native input](../archictecutre/21-native-input-format.md), [native records](../archictecutre/22-native-record-format.md), [activation and import](../archictecutre/23-native-activation-and-import.md), [placement and fleet control](../archictecutre/24-placement-execution-and-fleet-control.md), [parallel materialization and ranges](../archictecutre/25-parallel-materialization-and-ranges.md), and [custody, archive, and restore](../archictecutre/26-custody-archive-retention-and-restore.md).

Several substantial capabilities already exist and must not be proposed as if absent:

- Native activation/import, decoder floors, and deterministic replay are implemented. V1 compatibility is intentionally frozen.
- Range split, merge, movement, holder integration, chunked checkpoint seeds, archive retirement, and restore are connected to ledger/node paths. The range README is stale.
- Raft already has pre-vote, quorum checking, learners, joint configurations, leadership transfer, conflict handling, bounded inflight replication, ReadIndex, snapshots, priorities, and measured path/timing machinery.
- Shared physical WAL ownership and batching across logical groups exist. The fleet shares bounded workers rather than creating an unrestricted thread and WAL per session.
- Native follower materialization uses up to four workers in the production network composition; the leaf default of one is not the production setting.
- Managed V1 request generations already support bounded retirement/rotation. That does not imply equivalent native journal lifecycle support.
- There are real binary, QUIC, multi-node, crash-cut, custody, movement, history, and deployment tests. The problem is incomplete coverage of particular failure/resource boundaries and scale qualification.

## 4. Correctness, recovery, and resource admission

### F01 — P1: peer-loss feedback can turn retryable refusal into owner termination

**Evidence:** [fleet feedback and progress](../../crates/focal-node/src/fleet.rs), `report_lost`/`progress_group`; [grouped fleet error handling](../../crates/focal-node/src/fleet_group.rs), lines 421–429; [control owner](../../crates/focal-node/src/control_host.rs), lost-feedback/tick loop; [consensus guard](../../crates/focal-consensus/src/lib.rs), `report_unreachable`/`guarded_in`; [consensus reservation errors](../../crates/focal-consensus/src/memory.rs), lines 13–22; [replication driver](../../crates/focal-node/src/replication.rs), lines 136–146.

At the initial audit checkpoint, the driver posted a lost-peer notification after `PeerSendError::Lost`. `progress_group()` drained those notifications **before** checking/draining outstanding persistence. `report_unreachable()` went through the consensus mutation guard, which correctly returned `PersistencePending` while a Ready/checkpoint/decoder write was outstanding. The owner propagated that result with `?`; the grouped worker logged the error and stopped the session. The control owner similarly propagated lost-peer reports outside the tick's retryable-error handling and exited its run loop.

An isolated probe held the real shared WAL owner behind a replay callback, proposed an entry, and obtained `None` from `try_drain()`. Reporting peer 2 returned `Err(PersistencePending)` with `failed=false`. Releasing the writer then committed the entry normally. The consensus core was healthy; the then-current host converted a temporary refusal into termination.

The full suite built before the concurrent retry fix failed `placement_agent::tests::a_dead_voter_is_drained_and_replaced_without_waiting_it_out`. Its log reported the founder's session stopped with “durability is outstanding” and then failed to heal. A targeted rerun failed again with the same stop and unavailable founder replica. These are observed availability failures, separate from the initial sandbox socket errors. The evidence and fleet QUIC failover tests also failed in that full run but passed isolated reruns; those additional failures are timing-sensitive evidence, not three independently established root causes. Other enclosing tests passed despite logging the same stop, exposing a verification gap.

**Concurrent remediation, refreshed during the extension:** session/control loops gained retry handling and a paused-WAL session regression test. The current session branch also retains **`LedgerError::Consensus(ConsensusError::Capacity)`**, as well as pending durability, host capacity, and memory refusal. The nested consensus-capacity omission present at the first report checkpoint has been corrected. Section 12 preserves the earlier executions; section 14 distinguishes current source review from those historical results.

The earlier queue/reinsertion path lacked actual deduplication and could silently lose a retained report. Current `report_lost()` instead drains into a bounded sorted peer set, retains peers through retryable refusal, and counts coalescing/overflow. That source remedy closes the earlier reinsertion mechanism. Feedback remains a bounded hint; deterministic pressure and control/session coverage are still the appropriate closure evidence.

**Fix:** retain a bounded deduplicated set of pending peer feedback; apply it only when the group can mutate; retain entries on retryable capacity/persistence refusal; poll durability first and process a bounded number per worker slice. Count coalescing/overflow explicitly. Classify temporary host errors consistently for session and control owners.

**Acceptance:** deterministically pause the WAL, deliver dial/time-out loss feedback during Ready and LightReady, resume it, and verify both owners remain live and commit. Repeat during checkpoint/decoder-floor writes, membership changes, memory pressure, and duplicate feedback. Dead-voter replacement must pass without unexpected owner-stop diagnostics; a wider timeout does not fix the cause.

### F02 — P1: retirement can create a checkpoint that the same configuration cannot restore

**Evidence:** [retirement publication](../../crates/focal-core/src/native/retirement.rs), lines 679–807, particularly 751–754; [checkpoint count validation](../../crates/focal-core/src/native/record_codec/read_validate.rs), lines 195–254; [committed retirement application](../../crates/focal-ledger/src/native_session_apply.rs), lines 397–404.

`retire_native_family()` increments `meta.outcomes` and writes an outcome and new prefix, but does not enforce `self.limits.outcomes`. Recovery requires the outcome count to fit that limit and equal the native prefix. This creates an admission/recovery asymmetry.

The isolated native Core probe used `outcomes=3`, then created, cancelled, and released a claim. Retirement returned `Ok(14)` and advanced to prefix 4 with four outcomes. A structurally valid checkpoint could be encoded. Restoring it with the unchanged limits returned **`Contract(Capacity)`**. The small limit exercises the same code and comparison as the default million-outcome limit; a million-operation production run was not performed.

**Fix:** account for the retirement outcome before proposing/publishing retirement, including outstanding completion promises. Define deterministic behavior for a committed system record whose operation no longer fits. Rejecting only after durable commitment, stopping the owner, or publishing a state recovery rejects are inadequate. Existing over-limit states need an explicit supported repair/migration decision.

**Acceptance:** boundary tests at limit−1, limit, and limit+1; multiple families; pending completion reservations; WAL-only replay and checkpoint recovery; no publication on refusal. A permitted retirement must restore with exactly the same resource configuration and preserve every original request receipt.

### F03 — P1: network allocations precede the budget intended to bound them

**Evidence:** [frame buffer allocation](../../crates/focal-wire/src/frame.rs), lines 61–73 and 202–224; [QUIC request handling](../../crates/focal-wire/src/transport.rs), lines 488–516; [connection accounting](../../crates/focal-node/src/network_listener.rs), lines 294–299; [production limits](../../crates/focal-node/src/control_host.rs), lines 481–489; [node budget](../../crates/focal-node/src/network_service.rs), line 502.

An authenticated stream validates a frame header, then allocates and zero-fills the **entire announced payload** before any payload arrives and before `dispatch_accounted()` performs request admission. Nested decode allocations also occur before dispatch. The listener's 64 KiB connection charge is not a permit for these per-stream payload buffers.

Concurrent byte-buffer codec work now checks encoded lengths against available input and uses fallible exact byte allocation; its compatibility/malformed-length tests pass. That is useful decode hardening. It does not acquire the missing process/tenant ingress permit or change the full announced frame allocation above.

A header-only probe announcing 10 MiB allocated **10,485,760 bytes** while its payload reader remained pending. The production control limit permits 10 MiB frames. `for_consensus(128)` supplies a much larger stream allowance than the default 16; the relevant configured path permits roughly 1.4 GiB of application payload buffers on one fully occupied connection, before decoded objects and other owners. The production node budget is 1 GiB; generated pods have a 2 GiB memory limit. The aggregate allocation is a capacity calculation, not an executed OOM attack.

QUIC's stream receive window is already capped at 1 MiB: it should not be misreported as a 10 MiB window per stream. That transport improvement does not cap the application allocation above. Progress-aware payload waits also let a sender retain a full buffer by delivering 1,200 bytes per wait. At 30 seconds per wait, a 10 MiB frame can occupy memory for about 73 hours. Supporting slow useful transfers is reasonable; unpriced occupancy is the defect.

**Fix:** acquire a funded process/tenant/principal ingress-byte permit after the bounded header and before allocation; conservatively fund decoded shape; independently reserve control progress; bound stream admission by bytes as well as count. Release all permits on cancellation and malformed input. Price partial-transfer occupancy and useful progress without replacing every transfer with an arbitrarily short fixed deadline.

**Acceptance:** thousands of in-limit headers with absent/slow payloads must stay within a measured RSS envelope and leave node control/completion traffic live. Test nested vectors, decode refusal, revoked identities, stream cancellation, and role-incompatible requests. Compare actual allocations/RSS to accounted bytes, not just the budget counter.

### F04 — P1: normal native use exhausts the client journal after 256 lifetime operations

**Evidence:** [native journal limits and accounting](../../crates/focal-client/src/native_store.rs), lines 79–89, 455–461, and 599–627; [CLI store composition](../../crates/focal-node/src/cli/native.rs), lines 300–332; [native driver](../../crates/focal-native-client/src/driver.rs), lines 109–177.

The default native journal allows 256 operations. Capacity is computed from catalogue entries, not unresolved work. `record_delivered()` marks a journal delivered but never removes or archives the catalogue entry or returns its reservation. Ordinary CLI composition consistently selects the default limits; the journal interface is also used by the native MCP path.

A one-slot probe prepared an operation, recorded its committed receipt, and marked it delivered. `outstanding()` returned zero; usage remained one; the next unrelated prepare returned `Capacity`. Thus the default 256 is a **cumulative-use cutoff**, rather than a bound on concurrent unknown outcomes. A long-running participant reaches it while operating correctly.

**Fix:** provide a native journal lifecycle with durable acknowledgment, independently fenced generations, retention of exact-result lookup, and safe archival/reclamation. Managed V1 has useful lifecycle precedent, but native identity/outcome semantics need their own reviewed contract. Deleting the directory or raising 256 merely postpones or undermines retry guarantees.

**Acceptance:** ordinary CLI and MCP workflows must run well beyond the default window across process restarts and concurrent processes while keeping bounded live storage. Lost committed replies must still return the identical receipt; an old operation identity must never become an unrelated new operation.

### F05 — P2: expansion failure leaks a slot that pending-operation discovery cannot show

**Evidence:** [native prepare ordering](../../crates/focal-client/src/native_store.rs), lines 467–487 and 664–678; [resolution/compilation callback](../../crates/focal-native-client/src/driver.rs), lines 130–177.

Before resolving/compiling input, the store durably inserts an entry with `ready=false`. If the expansion callback fails, the claim remains. `outstanding()` skips not-ready entries. With an automatically generated operation ID, the driver returns the expansion error rather than the claimed identity. A missing object, temporary read failure, or compilation error can therefore consume permanent capacity without exposing a recoverable pending operation to the caller.

An isolated failed-expansion probe returned an error, zero outstanding operations, and catalogue usage one. No request had been sent.

**Fix:** make unexpanded identities discoverable with their authored intent and explicit recoverable state, or reclaim a proven never-ready/never-sent identity through a safe journal transition. Preserve crash recovery between identity claim and prepared-frame publication. Surface an assigned identity when work needs recovery.

**Acceptance:** repeatedly fail resolution before frame publication; occupancy must remain bounded/recoverable and the caller must be able to inspect every durable claim. Inject crashes at claim/prepared/ready boundaries; assert no frame escapes before durable Ready.

### F06 — P1: native journal updates have a cross-process time-of-check/time-of-use race

**Evidence:** [record_reply, record_delivered, and record_refusal](../../crates/focal-client/src/native_store.rs), lines 561–661; [directory lock ownership](../../crates/focal-client/src/operation_store/files.rs), lines 44–48 and native directory opening.

Each method calls `retry()`, which opens/locks the store, reads state, and returns after that lock is dropped. It then separately opens/locks the directory to write a journal derived from the stale state. Serialization of individual reads and writes does not serialize the transition.

Concrete interleaving: A reads “no receipt” in `record_refusal`; B records a committed receipt; A reacquires the lock and overwrites the journal with `receipt=None`, `delivered=true`, and a refusal. This directly contradicts the method's promise that a committed receipt is never overwritten. A delayed `record_reply` can likewise overwrite a newer delivered journal with generation 1 and `delivered=false`. Exact server-side retry identity may preserve the business outcome, but it does not excuse losing or regressing durable client knowledge.

**Fix:** hold one directory lock through reading the current journal, validating the transition, and durably replacing it. Enforce monotonic generation and committed/delivered precedence against the state read under that lock. Do not solve this with a process-local mutex alone.

**Acceptance:** deterministic multi-process interleavings for reply/reply, reply/delivered, reply/refusal, and crash during replacement. Once a matching committed receipt is durable it must remain the receipt forever; delivered state must never regress. No race reproduction was executed in this audit; the lock gap and overwrite path were inspected directly.

### F35 — P1: slow request bodies retain authority captured before certificate revocation

**Evidence:** [QUIC stream authentication and dispatch](../../crates/focal-wire/src/transport.rs), lines 508–516; [authenticated dispatch](../../crates/focal-wire/src/handler.rs), lines 121–155; [grant snapshots](../../crates/focal-wire/src/auth.rs), `PeerRegistry::authenticate`; [ordinary service routing](../../crates/focal-node/src/managed_service.rs), lines 300–313; [current revocation test](../../crates/focal-wire/src/tests.rs), lines 383–439.

Each stream clones an `AuthenticatedPeer` from the registry **before waiting for the header/body**. After the body arrives, `dispatch_accounted()` verifies the request against that old grant without consulting the registry again. Revocation removes the registry entry; it does not invalidate an already cloned peer. The ordinary managed service repeats the tenant check against the same snapshot. Specialized founder enrollment control has additional current-authorization checks; this finding does not assert those are bypassed.

A real loopback QUIC probe negotiated the normal protocol, sent only a request header, waited 100 ms, then revoked the actor certificate before sending any request payload. The registry denied a fresh authentication and the handler call count was still zero. Completing the payload then invoked the handler once and returned its response: `registry_denies=true, handler_calls=1`. This demonstrates post-revocation dispatch, not committed mutation or disclosure of real tenant data. A new stream started after revocation is refused, as the existing test verifies; the uncovered interleaving is revocation while a stream is still receiving.

F03's progress-based body wait makes this more than a tiny scheduling race: a peer can pre-open incomplete requests and retain the captured grant through a long useful-progress window. Changed tenant/role grants and expiry projection updates have the same stale-snapshot issue.

**Fix:** reauthenticate against the current local grant projection immediately before request dispatch/admission, after receipt of the complete frame; define and enforce any authorization lease/revision through subsequent queued admission. Make grant invalidation release waiting resources. Specify the treatment of work already durably accepted separately from incomplete network requests, preserving exact-result recovery. Distributed revocation has a propagation delay; an installed local revocation should not be ignored because a peer sent an earlier header.

**Acceptance:** revoke or restrict a grant during header receipt, partial body, queued admission, and exact retry; verify no newly admitted unauthorized request or tenant data is released. Test all ordinary participant roles and the specialized control/custody paths. Previously committed identities must retain safe recovery semantics under the explicit authorization policy.

## 5. Native queries, participant interfaces, and historical proof

### F07 — P2: evaluation continuation drops the boundary evaluation

**Evidence:** [evaluation page](../../crates/focal-node/src/native_reads.rs), lines 500–545.

The page skips `wire_key <= after`. Once the result count reaches `max_items`, it sets `next` to the current `wire_key` **before returning that evaluation**. A caller that supplies this continuation therefore skips that evaluation on the next page.

For ordered evaluations A, B, C and `max_items=1`: page one returns A and continuation B; page two starts strictly after B and returns C. B never appears. This follows directly from the two comparisons; it was not independently exercised through a populated network fixture.

**Fix:** define the cursor in terms of the last fully consumed key, or explicitly use an inclusive continuation. Prove iteration order matches cursor comparison, including declaration changes, target variants, missing rows, and generations.

**Acceptance:** concatenating pages at sizes 1, 2, and larger must equal an unpaged result without skips/duplicates, at one pinned prefix. Include exact-boundary pages, deleted/retired rows, and all evaluation targets.

### F08 — P2: the compiler selects a “current” evaluation from only the first page

**Evidence:** [resolution](../../crates/focal-native-client/src/driver.rs), lines 77–106; validation-context selection around 294–349; [evaluation selection](../../crates/focal-native-client/src/resolve.rs), lines 393–442; [server limits](../../crates/focal-core/src/native.rs), lines 219–223.

The driver requests evaluations with `after=None` and `READ_ITEMS=256`, extends objects from that page, and ignores `next`. The resolver then chooses the highest non-terminal matching generation **among those objects**. The core allows up to 4,096 evaluations per claim, so a valid current evaluation can be beyond this page. The caller can get a false missing-current error or bind an older still-live matching evaluation. Validation-context construction has the same first-page selection pattern.

This becomes particularly likely with many increments, targets, or superseded generations. Increasing `READ_ITEMS` does not provide bounded correctness for the larger supported domain.

**Fix:** prefer a server query for the exact target/current evaluation, backed by an index. Otherwise follow bounded continuation pages at a pinned prefix and report explicit capacity/incompleteness if the work bound is reached. Never interpret an incomplete page as the complete selection universe.

**Acceptance:** place the selected evaluation after item 256; exercise whole-work slots, admission, increments, several non-terminal generations, and concurrent publication. CLI and MCP must compile against the intended binding or return a truthful bounded-read refusal.

### F09 — P2: schema examples are normalized by the legacy decoder and rejected by native input

**Evidence:** [discovery commands and example normalization](../../crates/focal-node/src/cli/discovery.rs), lines 22–54 and 497–524; [strict native DTOs](../../crates/focal-client/src/operations/native_documents.rs); [native CLI document loading](../../crates/focal-node/src/cli/native_documents.rs).

`schema get` has a native selector, but `schema example` does not and normalizes through `operations::parse_json`, the V1 decoder. The generated `claim.submit` example contains `evidence_schemas`; native parsing rejects it as an unknown field. The isolated probe reproduced this with the current raw example and its actual typed normalization. Removing one incompatible field does not establish that the remaining deadline and native declaration semantics are correct.

Shape-only validation and operation name discovery similarly use the legacy operation registry, making native-only coverage and examples inconsistent. The current discovery tests validate examples against the registry that produced them, so they can pass while the native command rejects the result.

**Fix:** select the engine/version consistently for catalogue, schema, example, and local validation. Generate examples from the same contracts used by the selected CLI/MCP mutation path. Provide examples for native-only verbs and explicit compatibility output where needed.

**Acceptance:** pipe every generated native example through its real document decoder, compiler, and appropriate fixture-backed CLI/MCP path. At minimum, the advertised fresh-native quickstart must work verbatim without hand-editing generated JSON.

### F10 — P2: lineage output hides truncation and conflates a lower-bound observation with one prefix

**Evidence:** [lineage observation](../../crates/focal-native-client/src/observe.rs), lines 16–19, 61–172.

Lineage traversal is deliberately bounded to 16 ancestors and 64 related claims. It makes fresh relation-list requests with no cursor continuation, ignores list continuations, and drops extra related claims. The returned `NativeReadPage` has `next=None`, with no indication of either omitted ancestors or followers.

The first claim is linearizable; subsequent object reads use `AtLeast(first_token)`, and relation lists may observe still newer state. The final page carries the **first** token, native sequence, and logical time alongside those later objects. Its comment describes the lower-bound approach, so this is not evidence that the server's Exact or linearizable reads are broken. It is an interface ambiguity: a normal page-shaped value can be mistaken for a complete observation at one prefix.

**Fix:** expose a distinct composite observation type with explicit minimum/observed prefixes and truncation/continuations, or make the traversal genuinely pinned to one exact snapshot. Keep the work limits; make their effects visible.

**Acceptance:** deep chains, more than 64 followers, empty filtered pages with continuations, and writes during traversal. Output must distinguish complete lineage from a bounded sample, and every displayed prefix claim must match its stated semantics.

### F11 — P2: archival proof survives, but ordinary participant object resolution does not

**Evidence:** [object reads](../../crates/focal-node/src/native_reads.rs), lines 203–246; [retired document](../../crates/focal-node/src/native_documents.rs), `retired`; [generic content download](../../crates/focal-node/src/content_host.rs), lines 833–853; [retirement](../../crates/focal-core/src/native/retirement.rs).

Claim reads can return `NativeObject::Retired` with the archive bundle continuation. Artifact, definition, evaluation, and result reads look only in live Core rows; after family retirement they produce missing objects. The native client does not hydrate those rows from the bundle or transparently resolve the exact historical bindings through a dedicated archive query.

The bytes are not proven lost: generic tenant-scoped content download can fetch a known archive reference, and operator archive inspection exists. The gap is the participant-facing way to follow a previously accepted artifact/validation ID and recover the typed proof it refers to. A missing live object should not imply that accepted historical proof never existed.

**Fix:** offer an authorized, versioned archive continuation for historical object identities, plus bounded typed hydration or proof queries. Preserve identity, lineage, original prefix, schema verification, and custody checks. Make online versus archival latency explicit.

**Acceptance:** complete a two-party workflow, retain every exact binding, retire the family, restart/move the ledger, then retrieve its artifact, evaluation, result, and testament through normal client/CLI/MCP interfaces. Test denied tenant access and unavailable archive custody separately from unknown objects.

### F33 — P2: the native participant surface leaves existing content-transfer machinery inaccessible

**Evidence:** [native payload documents](../../crates/focal-client/src/operations/native_documents.rs), lines 938–944; [artifact compilation](../../crates/focal-native-client/src/compile.rs), lines 518–580; [native CLI routing](../../crates/focal-node/src/cli/native.rs), lines 235–241 and 907–909; [MCP catalogue composition](../../crates/focal-mcp/src/stdio.rs), lines 136–143; [file payload loading](../../crates/focal-node/src/cli/native_documents.rs), lines 33–57.

Authored native payloads support only inline bytes/text; compilation always produces `PayloadSpec::Inline`. The native CLI refuses chunked artifact upload and `get artifact --output` payload download. The MCP server deliberately omits its transfer tools when the backend is native. File input is read into an inline document under an explicit size bound; it is not a streaming/content-reference upload.

The wire/content service already has bounded resumable transfer and custody APIs, and the core supports content-pointer evidence. Their existence does not make them usable through the normal native CLI/MCP workflow. This also forces evidence bytes into authored JSON/frame/journal paths that could otherwise hold a small immutable descriptor. Large payloads hit interface/inline bounds, and even ordinary exact evidence lacks the advertised file-download convenience. This is a product integration gap, not evidence that an oversized payload is incorrectly accepted.

**Fix:** add a native authored content-reference form and native transfer tools that upload/seal under the correct schema/class and custody placement, then attach the exact immutable reference through the existing journaled mutation. Implement authorized payload download with verified identity and bounded streaming. Retain schema-specific payload limits; chunking is not permission to bypass a verifier's declared maximum.

**Acceptance:** native CLI and MCP upload, attach, and download valid file evidence; resume interrupted transfers and lost seals; preserve exact mutation identity after restart; refuse wrong schema/domain/class and missing custody. Measure journal/frame memory and replicated bytes with inline versus referenced evidence, including payloads near every interface/schema boundary.

### F34 — P2: native atomic creation batches stop at the core boundary

**Evidence:** [native command vectors](../../crates/focal-core/src/native.rs), lines 493–502; [authored batch checks](../../crates/focal-core/src/native/authored_prepare.rs), around lines 231–252; [single-claim compiler](../../crates/focal-native-client/src/compile.rs), lines 1511–1529; [authored operation inventory](../../crates/focal-client/src/operations/native_documents.rs); [CLI batch refusal](../../crates/focal-node/src/cli/native.rs), line 80.

The core's `Create`/`CreateAuthored` supports claim vectors with atomic batch validation. The shared native authored operation has no claim-batch variant, and its compiler reserves/pushes one claim. The native CLI explicitly refuses `submit claims`; the shared compiler omission also prevents a corresponding normal native MCP operation. Independent claim creation therefore requires separate journals, owner admissions, and proposals even where the caller needs a bounded atomic batch.

**Fix:** expose bounded authored native batches through one shared descriptor/compiler, including exact intra-batch identities, dependencies/parent bindings, duplicate-content checks, reservation quotes, and one retry identity. Define atomicity and per-item reporting explicitly. Keep batch byte/work limits and fair scheduling so one tenant cannot monopolize the owner.

**Acceptance:** multiple unrelated and related claims, duplicate IDs/content, invalid final item, graph cycles, parent/issuer authorization, capacity refusal, restart, and lost reply. Either the whole batch becomes the exact committed creation or none does. Measure actual end-to-end benefit; shared WAL batching alone does not provide application-level atomic creation.

## 6. Lifetime capacity, credentials, and storage performance

### F12 — P1: outcome retention makes native ledger capacity cumulative

**Evidence:** [default native limits](../../crates/focal-core/src/native.rs), lines 214–215; [request outcome admission](../../crates/focal-core/src/native/prepare.rs), lines 657–659; [retirement exclusions](../../crates/focal-core/src/native/retirement.rs), lines 117–137; [checkpoint count/prefix contract](../../crates/focal-core/src/native/record_codec/read_validate.rs), lines 249–254.

Every fresh native request increments the retained outcome count. The default limit is 1,000,000. Retirement removes live family rows but intentionally retains outcomes and creation results for exact retries; it also creates another outcome. Checkpoint validation requires outcome count to equal the native prefix. Consequently, freeing evidence/lifecycle rows does not restore fresh mutation capacity.

At a hypothetical 1,000 fresh mutations/second, one million outcomes is consumed in 16 minutes 40 seconds; at 100/second, about 2 hours 47 minutes. These are arithmetic illustrations, not measured throughput. Existing completion reservations must be preserved; this finding does not assume they are absent. The problem is an indefinitely used session's lifetime history becoming its active capacity bound, compounded by F02.

**Fix:** design exact historical receipt lookup and negative retry fences independently from resident live mutation state. Possible mechanisms include reviewed epoch/generation sealing with archived receipts, partitioned outcome storage, or a bounded resident index over durable historical proof. This changes a recovery invariant and requires a versioned contract; deleting dedup rows or simply enlarging the limit is unsafe/inadequate.

**Acceptance:** many more lifetime mutations than the live outcome window, with retirement, restart, leadership change, and historical exact retries. Live memory and admission should track unresolved/live obligations; historical proof must remain recoverable without re-executing old work.

### F13 — P1: the founder has an expiry horizon without a renewal/rotation lifecycle

**Evidence:** [default credential lifetime and founding issuance](../../crates/focal-enrollment/src/registry.rs), lines 23–31 and 547–588; [bootstrap PKI](../../crates/focal-enrollment/src/pki.rs), lines 56–80 and 117–125; [founder credential recovery](../../crates/focal-node/src/network_bootstrap.rs), lines 309–319; [renewal controller](../../crates/focal-node/src/network_controller.rs), lines 1172–1181 and 1346–1354; [credential renewal interface](../../crates/focal-node/src/credential_renewal.rs), lines 1–6 and 53.

The founder's **node credential defaults to 30 days**, using `EnrollmentLimits::credential_lifetime`. An isolated founding-enrollment probe produced that lifetime and returned `Expired` at its expiry boundary. The bootstrap enrollment server certificate is separately issued for 365 days and persisted in `authority.bin`; the CA is issued for ten years. The founder's automatic maintenance is explicitly skipped, and explicit founder renewal returns `Unsupported`. Startup also uses the persisted founding receipt and requires it still to authorize. The controller's retirement check applies to the founder as well. Reopening the authority does not replace its certificate. The probe verifies issuance/authorization behavior; a 30-day running cluster was not exercised.

Joined credential renewal/key rotation is implemented and should receive credit. It does not solve the founder's expiry, bootstrap enrollment endpoint's expiry, or CA rollover. A product meant to run continuously needs a supported path before these clocks expire, including after an outage or clock advance.

**Fix:** make founder credentials ordinary renewable node credentials where appropriate, separate bootstrap enrollment server identity from immutable genesis proof, and support issuer/root-trust succession and issuer recovery. Keep public committed authorization distinct from private signing-key custody. Do not defeat expiry checks or extend certificate lifetimes as the operating plan.

**Acceptance:** advance controlled time beyond the initial credential lifetime; renew ahead of expiry, restart before/after renewal publication, enroll a new participant afterward, and verify old certificates retire at the committed grace boundary. Exercise CA handoff, lost issuer recovery, and founder replacement with the original cluster identity intact.

### F14 — P1: shared-WAL checkpointing creates node-wide I/O and disk-headroom coupling

**Evidence:** [physical checkpoint owner](../../crates/focal-log/src/writer.rs), lines 1131–1172; [rewrite implementation](../../crates/focal-log/src/lib.rs), lines 356–395; [default checkpoint cadence](../../crates/focal-node/src/fleet.rs), `ReplicaConfig::new`.

A logical-group checkpoint reserves transient disk space equal to the **whole current physical WAL**, streams every unrelated group's record into a new generation, writes the target checkpoint, installs the fence, scans the new generation again, and cleans up the old generation. The shared physical writer performs this work synchronously, so it blocks other groups' append/replay commands until it finishes. Async receipts free fleet workers; they do not make this disk owner concurrent.

With many active groups reaching their 4,096-entry checkpoint cadence, each can repeatedly rewrite all other groups. This amplifies bytes read/written and couples a small session's compaction to the largest neighboring histories. A near-full disk can cleanly refuse checkpointing even when compacting that one group would release space, because the replacement requires whole-log headroom. The clean refusal is good; the operating envelope is poor.

**Fix:** retain shared batching but introduce segmented retention with per-group durable floors and a durable manifest. Reclaim obsolete segments incrementally, or coordinate/checkpoint multiple groups per generation. Run bounded background compaction with I/O quotas and preserve crash-safe old/new generations until publication. Avoid reverting to one unrestricted physical writer per logical session.

**Acceptance:** many hot/cold groups, a large old WAL, constrained free space, concurrent heartbeats/appends, and crashes at every manifest/fence/cleanup cut. Measure checkpoint bytes per reclaimed byte, append p99, and maximum extra disk required. A small group's checkpoint should not force unrelated history-sized work indefinitely.

### F15 — P2: Raft catch-up allocates for the suffix rather than the requested page

**Evidence:** [stable entry fetch](../../crates/focal-consensus/src/storage.rs), lines 383–407; [unstable log slice](../../crates/focal-raft/src/log.rs), lines 521–550.

Stable fetch reserves `high-low` entry slots before applying `max_bytes`. Unstable slicing copies the entire selected suffix, then calls `limit_bytes()`. The returned page is small, but its temporary allocation and retained vector capacity are not bounded by that page.

The public log probe used 1,024 unstable entries with 4 KiB payloads and a 4 KiB page budget. It returned one entry but requested **4,268,032 allocated bytes** and retained capacity for **1,024 entries**. This is total allocator-requested bytes during the operation, not a measurement of process RSS or a release throughput result.

Repeated catch-up pages can repeat suffix-sized copying, approaching quadratic work over a lagging replica's backlog; many peers and an inflight window amplify the pressure. The performance guard then has to budget that unnecessary peak.

**Fix:** select the byte-limited prefix before allocating/cloning; retain Raft's at-least-one-entry behavior for an oversized first entry. Reserve only the selected count, and combine stable/unstable byte accounting correctly. Preserve owned buffers required by the Ready/persistence contract.

**Acceptance:** allocation counts/bytes and retained capacity for long stable, unstable, and mixed tails; page budget zero/small; first oversized entry; snapshots and compaction. Catch-up temporary memory should scale with the page and bounded metadata, not the whole backlog.

### F16 — P2: heartbeat-sized work requests history-sized staging and accounting

**Evidence:** [staging calculation](../../crates/focal-consensus/src/memory.rs), lines 128–149; [guarded mutations](../../crates/focal-consensus/src/lib.rs), lines 1389–1405; [persistence staging](../../crates/focal-consensus/src/persistence.rs), lines 74–116; [resident accounting](../../crates/focal-consensus/src/storage.rs), `resident_bytes`.

Every guarded tick, campaign, read barrier, report, or incoming step computes a conservative allowance containing twice resident history, per-member batch/snapshot space, and multiples of raw state. Resident-byte helpers also inspect retained collections. Even a small control transition can require substantial temporary headroom and history-counting CPU. As logs grow, the node may refuse control progress at capacity although the logical operation is tiny.

This guard exists to cover real copies and should not be weakened blindly. F15 removes one reason for its large allowance, but operation-specific funding remains necessary for a predictable control lane. The claimed liveness consequence here is a static capacity risk; no threshold/heartbeat stall benchmark was performed.

**Fix:** maintain checked resident-byte counters incrementally; precompute exact bounded outgoing work; distinguish tick/read/report staging from proposal/snapshot staging; fund a minimum control transition separately. Bound the number of history walks per tick and verify transient peaks empirically before reducing reservations.

**Acceptance:** fixed-size heartbeat/read/report operations over increasing histories and under near-limit ordinary pressure. Control p99 and required free bytes should have an explicit bound; failure must be retryable and must not terminate owners.

### F17 — P2: the persistence pipeline leaves avoidable latency on the Raft critical path

**Evidence:** [Ready/LightReady state machine](../../crates/focal-consensus/src/persistence.rs), lines 225–380; [WAL append fence](../../crates/focal-log/src/lib.rs), lines 517–524 and 610–625; [mutation fence](../../crates/focal-consensus/src/lib.rs), lines 1383–1387.

The current implementation intentionally prevents further group mutation while its durable Ready is outstanding. Ready records persist before advance; a LightReady commit change can require another ordered hard-state write before committed application output is released. A single-voter mutation can therefore require two physical durability cycles. A physical cycle syncs active data, the replacement fence file, and directory publication, subject to platform-specific implementation. Shared group commit amortizes cycles across groups; it does not remove the two-phase dependency within one group.

Leader outbound replication is also released through this durable event path. Established Raft can overlap leader disk persistence with follower replication while ensuring the leader's own match index represents durable entries, and follower acknowledgments remain persistence-dependent. That is an implementation redesign, not permission to send durable success early. [Ongaro's dissertation, section 10.2](https://web.stanford.edu/~ouster/cgi-bin/papers/OngaroPhD.pdf) describes the relevant overlap and batching principles.

**Fix:** first measure Ready-to-fence, fence-to-send, quorum-to-apply, and client-journal latency separately. Evaluate an asynchronous Ready contract with safe immediate versus persistence-dependent messages, bounded group commit by both bytes and latency, and a reviewed single-voter commit/fence optimization. Keep read publication and exact receipts behind the required durability boundary.

**Acceptance:** crash cuts before/after each disk fence and message class, disk stalls, concurrent election/configuration changes, and black-box exact-result histories. Benchmark release binaries on representative filesystems. Do not delete `fsync`, let speculative self-acks count toward quorum, or relax publication to obtain a favorable microbenchmark.

### F18 — P2: immutable event history participates in hot lifecycle page copying

**Evidence:** [namespace selection](../../crates/focal-core/src/native.rs), lines 1075–1100; [row-copy logic](../../crates/focal-core/src/native/prepare.rs), lines 121–124 and 148 onward; [existing allocation qualification](../qualification/allocations-2026-09-29.md).

Definitions, artifact descriptors, claim content, creation results, legacy rows, and indexes have separate page namespaces. `Meta`, mutable claim/lifecycle rows, events, and outcomes still fall into namespace 0. A COW write touching hot state can therefore copy immutable event rows sharing an affected page; events and claims have fallible owned-copy paths, including dynamic content.

The existing allocation report is useful corroboration of allocation costs, but its dated measurements are not fresh measurements from this audit. This is a remaining layout opportunity after prior descriptor/page improvements, not a claim that all native state is deep-cloned for every operation.

**Fix:** separate immutable event/outcome history from hot lifecycle/control pages; tune page layouts and affinity using measured touched-page counts. Preserve checkpoint layout/proof compatibility or version the affected layout. Prefer shared immutable pages and borrowed views over adding a reference-counted owner to every tiny row.

**Acceptance:** lifecycle updates over large retained histories must copy only a bounded hot working set; compare allocated bytes, page clones, resident peaks, and replay/checkpoint hashes for serial and parallel materialization.

### F19 — P2: evidence downloads repeat whole-manifest work for every byte page

**Evidence:** [range reads](../../crates/focal-evidence/src/store.rs), lines 768–825; [manifest verification](../../crates/focal-evidence/src/store.rs), lines 1010–1044; [download dispatch](../../crates/focal-node/src/content_host.rs), lines 833–853.

Each `read_range()` reloads, hashes, decodes, and validates the whole manifest, then scans chunk offsets from the beginning until it reaches the requested range. Downloading an N-chunk object as small successive pages performs O(N²) cumulative manifest/chunk-metadata work, besides repeated manifest I/O. It verifies the needed data chunks correctly; the cost of locating them is the issue.

Node custody transfers already have useful retained-manifest machinery, and `read_verified` now reuses a scratch buffer. Those improvements should not be re-reported as missing. The ordinary paged-download path still repeats the work above.

**Fix:** bounded authenticated manifest caching or a leased download plan, with cumulative offsets and direct/binary-searched chunk lookup. Separate response page size from stored chunk indexing. Cache validation provenance under the immutable manifest digest, and continue verifying each delivered data chunk.

**Acceptance:** sequential and random ranges on increasing chunk counts; allocation/I/O totals proportional to transferred bytes plus bounded/indexed metadata work; corrupt/replaced chunk files, lease expiry, and cold cache. Tenant authorization must precede any reusable content plan.

## 7. Cluster admission, authority, deployment, and operations

### F20 — P1: the global connection cap prevents the admission policy from doing its job

**Evidence:** [node listener outer cap](../../crates/focal-node/src/network_listener.rs), line 294; [generic QUIC listener](../../crates/focal-wire/src/transport.rs), line 344; [identity admission](../../crates/focal-wire/src/admission.rs), lines 1–47; [default wire limit](../../crates/focal-wire/src/message.rs), line 785.

Admission separates pending handshakes from authenticated identities and replaces an identity's least-used connection at its own limit. The outer listener counts **all** live connection futures and refuses newcomers at `max_connections` before authentication or identity replacement can occur. Thus full established occupancy also consumes the opportunity to authenticate a replacement.

With default limits, eight participant identities holding 16 connections each can fill the 128 outer places. A restarting node or a participant replacing its own stale connection cannot reach identity-aware admission. This does not require one identity to bypass its 16-connection bound. Enrollment shares the node listener's outer bottleneck as well.

**Fix:** bound pending handshakes separately from established connections, with explicit aggregate memory accounting and node/control headroom. Let the bounded handshake stage identify an eligible same-identity replacement even at active occupancy. Reserve classes fairly, including enrollment, without making the pending pool an unbounded back door.

**Acceptance:** fill participant capacity, restart a voting peer, replace a same-principal connection, enroll a node, and run half-open/malicious handshakes concurrently. Existing healthy peers and required reconnection must retain bounded latency; all refusals must be observable.

### F21 — P1: root authority and cluster topology remain global whole-state bottlenecks

**Evidence:** [authority state and defaults](../../crates/focal-directory/src/authority.rs), lines 48–80; [authority snapshot](../../crates/focal-control/src/authority.rs), lines 210–225; [grant/route installation](../../crates/focal-node/src/network_controller.rs), lines 305–331 and 1475 onward; [liveness membership](../../crates/focal-node/src/liveness/driver.rs), lines 36–45.

Directory partitions and delegation exist, but infrastructure authority still maintains node and log-group maps with defaults of 1,024 nodes and 4,096 groups and an 8 MiB checkpoint. Partition authority snapshots clone the full infrastructure registry and enrollment checkpoint. Controllers build certificate grants and contact routes from the full corresponding state; liveness tracks a 1,024-member map.

These are sensible bounds for an operating unit; they are not a global control plane. The current root-level assignment/refresh path is the central constraint even if session records are independent and directory row storage is partitioned. Liveness uses SWIM-style bounded probes/gossip; this finding does not allege naive all-to-all broadcast. It concerns global membership materialization and authority distribution.

**Fix:** make the existing bounded unit an explicit cell. Delegate infrastructure group/node authority and enrollment to region/cell authorities with proof of parent authorization and versioned succession. Route through regional directories and bounded caches, distribute incremental revisions, and keep local liveness neighborhoods. The global root should manage bounded cell authority/delegation records rather than every session and machine.

**Acceptance:** add cells without growing every node's resident node/group/certificate map; operate a cell through parent unavailability within explicit lease/authority rules; fence revoked cell epochs; recover and converge routes after moves. Raising these constants is not proof of global scalability.

### F22 — P1: identity churn eventually exhausts enrollment even at low live occupancy

**Evidence:** [enrollment bounds](../../crates/focal-enrollment/src/registry.rs), lines 13–45; invitation checks at 763/824; certificate check at 846; persisted records and changes at 96–146 and 442 onward.

The default registry bounds invitations and enrollments at 4,096, with an absolute invitation ceiling of 65,536. Invitation records remain after consumption, revocation, and expiry, and enrolled identity records remain in the authoritative registry. Expired previous certificates from renewal have their own grace cleanup; that does not reclaim old invitations or historical identities.

At global scale, ordinary machine replacement, failed onboarding, short-lived actors, and revocations are steady-state behavior. A bound on cumulative issued records turns a security/administrative history into permanent fresh-admission failure even when the active population fits comfortably.

**Fix:** partition issuance and authorization; compact closed invitation generations under durable rejection fences; separate active authorization from immutable issuance/revocation history. Preserve exact redeem retries and prevent old tokens/certificates from regaining meaning. Tie cleanup to committed state and issuer epochs, not wall-clock deletion alone.

**Acceptance:** lifetime onboarding far beyond one active-window bound, mostly expired/revoked/consumed invitations, repeated restart, token replay, grace-overlapping rotations, and concurrent joins. Active authorization and checkpoint sizes must remain bounded while historical audit evidence remains available.

### F23 — P2: every authority change pays for unrelated topology state

**Evidence:** [authority prepare](../../crates/focal-directory/src/authority.rs), lines 225–295, especially 277–282; [control snapshot estimate](../../crates/focal-control/src/authority.rs), lines 216–236.

Preparation reserves the full current authority state plus extra bytes, then deep-clones `self.root.state`, including all node and group maps. Even `AdvanceClock` takes this path. A stream of node renewal/topology/group updates therefore costs O(total nodes + groups) per change. Copying and serializing whole authority snapshots adds another growing cost downstream.

**Fix:** persistent/paged map roots or bounded owned deltas with atomic publication; indexed expiration/clock work; incremental snapshot distribution. Preserve revision lineage, compare fences, and rejection rollback. The COW work already done in other stores does not automatically cover this registry.

**Acceptance:** one changed grant and clock advancement over increasingly large registries; measure allocation, copied bytes, checkpoint bytes, and preparation latency. Cost must reflect changed/touched pages, with unchanged topology shared safely.

### F24 — P1: data-plane zone survival does not establish control-plane zone survival

**Evidence:** [deployment changes](../../crates/focal-node/src/deployment/plan.rs), lines 69–84; [KIND campaign's metadata result](../qualification/campaigns/2026-09-29-kind.md), section “Defect D5”; [cluster administration](../cluster-admin.md).

The deployment planner changes policy and plans session placement. It does not include a corresponding root-voter durability plan. The recorded KIND campaign obtained three session voters across zones while root metadata remained a single founder voter and the other hosts remained learners. Losing the founder preserved session read availability but interrupted metadata/placement/membership operations until it returned.

Manual root promotion exists. It is not part of a verified whole-product guarantee returned by session placement. Nor does root promotion alone provide private issuer availability: public metadata replication and certificate signing-key custody have different failure requirements.

**Fix:** model and report separate guarantees for session ordering, range state, evidence/archive custody, directory partitions, root infrastructure authority, and issuer service. Expand/enforce root and required partition voter placement when a deployment requests fault-domain survival. Make any remaining weaker issuer/recovery requirement explicit in the achieved guarantee and blockers.

**Acceptance:** after the deployment reports the requested zone/region guarantee, lose each required domain in turn and exercise existing reads/writes, new session creation, placement repair, credential renewal, enrollment, and archive lookup. Availability must match the actual component-level promise.

### F25 — P2: readiness is wired to the deliberate process-alive probe

**Evidence:** [Kubernetes renderer](../../crates/focal-node/src/deployment/render/kubernetes.rs), lines 415–420; [Helm probes](../../deploy/helm/focal/templates/_helpers.tpl), lines 151–165; [alive probe semantics](../../crates/focal-node/src/cluster_admin.rs), lines 1060–1073.

Startup, liveness, and readiness all execute `cluster node probe --check alive`. That probe intentionally reads only identity and avoids root/session/placement state. This correctly prevents a missing quorum from provoking a liveness restart cascade. It also means a pod with stopped serving owners can remain Ready while its process/admin identity is responsive—particularly relevant to F01.

**Fix:** retain the independent alive liveness probe. Add serving readiness based on the node's intended role and required local owners, initialization, fencing, and routing/custody state. Do not require every follower to be leader or make transient quorum loss cause liveness failure. If peer discovery must include not-ready pods, make that service setting deliberate and separate from client readiness.

**Acceptance:** alive but stopped session/control owner; learner catch-up; initial enrollment; fenced binary; healthy follower; temporary quorum loss. Readiness must reflect the defined serving contract without causing supervisor-induced quorum collapse.

### F26 — P2: large session populations outgrow the fixed metrics view

**Evidence:** [session metrics ceiling](../../crates/focal-node/src/metrics.rs), line 19; [sampling](../../crates/focal-node/src/network_service.rs), lines 1231–1238; `sessions_truncated` rendering in [metrics](../../crates/focal-node/src/metrics.rs).

The sampler stops after 512 sessions. It truthfully exposes a truncation flag, which is good, but a larger fleet's remaining session health and peer failures are absent from the sampled view. A fixed first subset can hide the hot or failing tail indefinitely. Existing WAL, admission, timing, and unreachable-peer metrics are valuable; they do not provide a complete aggregate account of all groups or per-operation end-to-end tail latency.

**Fix:** always maintain bounded low-cardinality aggregate health/capacity counters across all owned groups; expose paged/sharded or rotating detailed session samples. Add bounded histograms for queue delay, fsync/fence, quorum, apply, custody, ingress occupancy, retry reasons, and client-observed latency. Separate refusal due to overload from corruption/fencing and owner termination.

**Acceptance:** put the only failed/hot group outside the first 512; aggregate metrics and alerts must still reveal it. Memory/cardinality bounds must hold at thousands of groups and under identity/session churn. Accounted network bytes should be compared with real RSS.

### F27 — P3: the production no-panic gate permits local opt-outs

**Extension status:** concurrent work added [a source-policy check](../../scripts/check_production_policy.py), negative/positive fixtures, and a mandatory invocation from `check-production.sh`; the unconditional load-tool allowances were removed. The extension's policy run passed for 1,061 production sources and executes its fixture self-test. The original observation below describes the earlier tree, not the current enforcement path. No new full workspace gate run is implied by that focused result.

**Evidence:** [stated workspace policy](../../CLAUDE.md), section 1; [production check](../../scripts/check-production.sh); [load binary allowances](../../tools/load/src/main.rs), lines 1–16 and 40–54.

The policy explicitly includes measurement/test-support crates compiled outside test modules. **Fix:** enforce the required lints with a level or source-policy check that cannot be locally bypassed for covered targets, or document and narrowly enumerate approved tooling exceptions. Keep test-only allowances scoped to test builds. Align wording, implementation, and what CI's green check actually proves.

**Acceptance:** a small negative fixture with an unconditional production `allow` and prohibited operation must fail the policy check; an approved test-only fixture must pass. Removing the fixture should leave all normal targets passing.

### F28 — P1: qualification currently supports correctness journeys, not the requested global capacity claim

**Evidence:** [capacity envelope](../qualification/capacity-envelope.md); [dated allocation report](../qualification/allocations-2026-09-29.md); [workload driver](../../tools/load/src/driver.rs); [workload shape](../../tools/load/src/shape.rs); [nightly gates](../../.github/workflows/nightly.yml); [CI](../../.github/workflows/ci.yml).

The capacity document correctly labels global figures as an envelope. Some supporting explanations are now stale: legacy reduction numbers are presented alongside current native range recommendations, and independent sessions are described as having independent serial owners/counters even though production fleet workers, ancestor budgets, WAL, and transport are shared. Independent logical ordering does not mean zero physical contention.

`focal-load` uses an embedded in-process node, creates claims, and then issues reads. Its shape does not cover real multi-node QUIC, concurrency mix, evidence transfer, lifecycle churn, placement repair, or WAN faults. Nightly campaigns and extensive Raft/model/crash/history tests provide valuable correctness evidence, but successful completion alone is not a p99/RSS/throughput regression gate. Local simulated regions and a small KIND deployment do not establish global operation.

**Fix:** create release-binary capacity and soak qualification with declared workloads, hardware, topology, filesystem, failure domains, and SLOs. Gate both correctness and resource/tail-latency envelopes. Refresh capacity claims from current native/shared-owner code. The test matrix in section 10 specifies concrete closure work.

**Acceptance:** sustained bounded operation under live-state and historical churn; measured replication/custody/compaction amplification; fault recovery within a stated RTO; unchanged exact-result histories; versioned artifacts and machine-readable regression comparisons. No extrapolation from a RAM microbenchmark should be labelled demonstrated cluster capacity.

### F29 — P3: documentation sends readers toward obsolete implementation assumptions

**Evidence:** [main README](../../README.md), “IMPORTANT”; [range README](../../crates/focal-ranges/README.md), opening and enabling checklist; [node README](../../crates/focal-node/README.md); [remaining-work handoff](../REMAINING.md), historical unfinished-source table; [actual native Session integration](../../crates/focal-ledger/src/native_session.rs).

The main README says automatic placement, range movement, archival/restore, Kubernetes packaging, and multi-region operation are still being built without distinguishing implemented journeys from unqualified requirements. The range README says it is not connected to node write/recovery/placement/transport paths, contradicting the integration. Historical remaining-work tables still describe missing files/modules that now exist. Some module comments describe dormant/unregistered codecs that are used by active native sessions.

These are consequential navigation errors for contributors and agents. They also encourage audits to recommend completed features and obscure which remaining work is qualification versus implementation. F09 is the executable manifestation of similar contract drift.

**Fix:** maintain a short current capability matrix with engine, supported interface, operating envelope, qualification reference, and remaining limit. Keep historical handoffs/campaigns clearly labelled historical; link them from current statements without treating old observations as current state. Update entry READMEs and active module contract comments.

**Acceptance:** a new contributor can trace fresh-native startup, multi-party evidence, distributed placement, range movement, retirement, and restore from current entry docs to executable tests. Contract/link validation should supplement, not replace, semantic documentation review.

## 8. Participant runtime, memory mechanics, and hot-ledger architecture

### F30 — P2: stuck participant handlers cannot be forcibly cancelled or resource-contained in process

**Evidence:** [handler worker pool](../../crates/focal-runtime/src/pool.rs), lines 44–86 and 130 onward; runtime `Executor`, cancellation, and reconciliation contracts.

Workers execute synchronous callbacks on OS threads. Cancellation is cooperative. A handler that never returns can occupy a worker indefinitely; dropping the pool detaches an unfinished thread instead of blocking shutdown. Its allocations, external calls, and CPU are outside the ledger's bookkeeping permits. A late external effect can continue after the logical attempt deadline, so the reconciliation contract is essential.

This is an intentional embedding constraint and does not mean the Focal daemon executes untrusted agents. It matters when integrations use this pool for arbitrary or failure-prone tools and assume timeout restores worker capacity or stops side effects.

**Fix:** offer a supervised process/container executor option with bounded concurrency, memory/CPU, kill/reap behavior, and durable run/attempt identity. Keep the in-process path for trusted cooperative code and document its resource guarantees precisely. External effects still require idempotence/reconciliation; killing a process does not prove an effect never occurred.

**Acceptance:** hung, cancellation-ignoring, allocating, and crashing handlers; all-worker exhaustion; restart while an external outcome is unknown. Other work must retain its promised capacity, and unknown effects must never be automatically repeated without the required proof.

### F31 — P3: arena page-directory growth has quadratic cumulative copying

**Evidence:** [arena growth](../../crates/focal-memory/src/arena.rs), lines 309–323.

Adding one page allocates a new directory of length `old_len+1`, moves every existing page descriptor into it, and replaces the old directory. Over P pages this moves O(P²) descriptors and requests a new directory on every page. Payload pages themselves are not copied, so this is a smaller metadata cost, but it becomes visible for very large arenas.

**Fix:** grow the directory with a bounded, charged capacity policy and `try_reserve` before mutation, or use a segmented directory. Preserve failure atomicity, peak-memory accounting, stable generational handles, and the non-reuse guarantee.

**Acceptance:** increasing arena sizes must show near-linear cumulative directory work and a bounded transient peak; allocation refusal must leave the old directory and handle behavior intact. Existing generation-exhaustion tests remain essential.

### F32 — P1: range parallelism does not remove a hot session's sequencing ceiling

**Evidence:** [range/materialization contract](../archictecutre/25-parallel-materialization-and-ranges.md), sections 1, 2, and 7; [native range bound](../../crates/focal-core/src/native.rs), `max_ranges: 64`; [production worker setting](../../crates/focal-node/src/network_service.rs), lines 1865–1880; [fleet worker](../../crates/focal-node/src/fleet_group.rs).

Admission and ordering remain serial at the session leader. Native follower staging can run in dependency waves, and range holders can hold subsets, but the session's ordered log still reaches its members. A holder is a learner of that session, not a new independent write sequencer. The default 64-range bound and up-to-four replay workers provide finite parallelism, not unbounded throughput for one globally hot session.

This is compatible with the product's independently ordered-session architecture. The missing operating contract is quantitative: maximum sustainable mutations, evaluation/receipt fanout, retained rows/history, read rate, and recovery time **per session and per cell**, including a single hot affinity/control namespace. Adding nodes cannot be assumed to multiply a hot session's write capacity.

**Fix:** make independently ordered sessions/cells the primary scale unit. Define supported hot-ledger limits and overload behavior, and measure when splitting state helps versus when sequencing, control affinity, WAL, or log delivery dominates. Where workloads need a single global order, state its latency/throughput cost explicitly. Introducing multi-leader or cross-session atomicity changes protocol semantics and needs a separate design, not an opportunistic performance patch.

**Acceptance:** hot single claim, many independent claims within one session, many independent sessions, dense dependency graphs, and large evidence verification, with local and WAN quorums. Publish both the single-session ceiling and fleet aggregate results; all advertised configurations must preserve exact ordering and acceptance semantics.

The Raft implementation's 128-message inflight window should be assessed together with actual bounded send pages, stream credits, memory and disk residence, rather than increased independently.

The optional fast track has code, simulations, and a TLA+ model. `NodeConfig::joining` defaults it off; the inspected node/ledger/control production paths do not call `propose_fast`. Do not project its core benchmark improvements onto the normal product. Any activation needs an end-to-end wire/WAL/decoder-floor and failover qualification, explicit quorum-size tradeoffs, and a workload for which the extra recipients improve actual commit latency. The existing [consensus roadmap](../archictecutre/27-consensus-roadmap-and-slates-port.md) and [Slates delta review](../qualification/slates-delta-2026-09-29.md) provide useful provenance; they are not evidence that the normal binary routes client work through it.

For globally distributed linearizable writes, place each ordinary session's quorum according to its explicit fault-domain guarantee and workload locality. A geographically distributed majority incurs network latency determined by the quorum that must actually participate; removing this cost while preserving the same semantics is not a transport tuning knob. The [Raft paper](https://raft.github.io/raft.pdf) describes majority-based commitment and configuration safety. Use asynchronous cross-cell discovery/read projections only where their staleness is explicit; keep acceptance and exact-result authority with the ordered session.

## 10. Scale qualification and operating design

### 10.1 Required scale units and invariants

The workable global design is a hierarchy of bounded units:

1. **Laptop:** one node/disk; honest disk-loss durability; bounded native journal generations; bounded evidence; recoverable checkpoints; useful admission under memory/disk pressure.
2. **Cell:** a bounded set of nodes and independently ordered ledgers; local infrastructure/enrollment authority; a fault-domain-aware metadata quorum; shared WAL/owner isolation with measured capacity; bounded routing and liveness neighborhoods.
3. **Region:** discovery and placement over cells, explicit delegated authority and proof succession, locality-aware ownership, aggregate quotas, and bounded caches. A regional failure cannot require scanning every global session on every surviving node.
4. **Global:** a bounded directory of regional/cell authority, placement policy/residency constraints, historical proof discovery, and operations that explicitly define which failures/latencies they tolerate. Global session/node identity should not imply global all-node resident state.

Delegation, split/move, and partitioning already provide pieces of this design. The work is completing authority/enrollment locality, measuring shared physical bottlenecks, and proving operation at the unit boundaries. “Meta scale” should be expressed as sessions/second, active and historical sessions, evidence bytes/second, identities/day, concurrent reads, regions/cells, p99 latency, repair RTO, and retained proof horizon. The repository currently cannot honestly supply all those achieved figures.

Preserve these contracts through optimization:

- One accepted mutation has one exact durable outcome; uncertain transport completion never becomes a different request identity.
- Committed application publication is a complete prefix, including parallel materializers and moved holders.
- Exact evidence/validation identities survive archival and remain retrievable through authorized interfaces.
- Completion obligations remain funded while ordinary admission is refused.
- Stale route, placement, incarnation, decoder, and authority epochs cannot regain authority after cleanup.
- Metadata ordering, content custody, and private signing-key custody have independently checked guarantees.
- Disk/memory/connection limits govern actual retained work, including before decoding and during compaction/recovery.
- Losing one cell or region does not force an unbounded global repair burst or invalidate unrelated cells' valid authority.

## 13. Remediation order and closure criteria

1. **Restore reliable failure handling and recovery:** F01/F02; close the failing dead-voter test and add deterministic pending-durability/retirement-boundary coverage. Inspect other new host mutations for the same retryable-error propagation pattern. A healthy node must not stop because its disk is still writing.
2. **Make ordinary participant operation sustainable:** F04–F06/F09; bounded native journal generations, recoverable failed expansion, atomic journal transitions, engine-correct examples. Validate through ordinary CLI and MCP beyond the current window, not just a low-level store test.
3. **Close actual resource/connection/authorization admission holes:** F03/F20/F35, then F15/F16. Funding must precede allocation; dispatch must use valid current authority; control and reconnection must retain usable headroom under bulk work and memory pressure.
4. **Fix native reads and historical proof access:** F07/F08/F10/F11. Paginate/resolve completely under explicit bounds and expose archive continuation and composite/truncated observations truthfully. Complete native content transfer and bounded atomic creation interfaces (F33/F34) using the existing custody and core batch contracts.
5. **Finish continuous-use and fault-domain guarantees:** F12/F13/F22/F24/F25. Outcome/enrollment retention, founder lifecycle, metadata quorum/issuer guarantees, and serving readiness need coherent operating contracts.
6. **Remove physical amplification and measure critical paths:** F14/F17–F19/F23/F31. Preserve shared batching and proof/fence semantics while making work proportional to useful pages/changes.
7. **Qualify the global architecture:** F21/F26/F28/F32. Delegated cells, bounded per-node topology, truthful component-level guarantees, tail-latency/resource campaigns, and published single-session/cell ceilings. Then refresh entry documentation and enforce the actual policy gates (F27/F29).

A credible completion report should attach the regression tests, exact workload/topology, resource and tail-latency results, crash/history evidence, and updated operating guarantees for each closed finding. Treat a larger limit, a longer timeout, a quiet log, or a renamed guarantee as a change to be reviewed—not as closure by itself.
