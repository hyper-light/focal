# Replication connection pool

`PeerConnectionPool` accepts FleetHost's outgoing `(target_node, RequestEnvelope)` pair. It accepts only `Operation::Raft` and retains the exact request identity, group and encoded message across bounded retries. It does not parse, rewrite or acknowledge the Raft message itself.

Create the pool with a node's `QuicConnector` and `PeerPoolLimits`, then install a complete `BTreeMap<u64, PeerEndpoint>` using `replace_routes(control_revision, routes)`. Each endpoint carries a concrete socket address and the expected certificate server name. The connector performs normal mutual TLS authentication. Same-revision snapshots must be identical; lower revisions are rejected. Replacing/removing an endpoint retires its cached connection, fences active sends and prevents their result from appearing as delivery to a new route. In-band redirects never modify these routes.

Routes describe reachability only. The control owner must authorize node identities and assignments separately. Incoming node ingress must check authenticated sender identity against the encoded Raft sender and the current group configuration. A successful `send` means the remote ingress accepted a transport packet; it does not establish a durable log acknowledgment, snapshot completion, quorum or commit. Those facts arrive only through the consensus protocol's own messages and persisted state.

The pool has no internal packet queue. A global inflight semaphore, per-peer permits, bounded route map and a physical connection semaphore bound its work. Connection establishment is shared per peer; at most the permitted callers can await it. Idle cached connections are evicted when necessary. Removed connections retain their physical reservation until their active send tasks release it, so changing a route cannot temporarily exceed the connection budget.

FleetHost owns its separately bounded egress queue and bounded drain concurrency. `Busy`, route errors, timeouts and other losses discard an individual transport attempt; Raft retransmission is responsible for recovery. The pool makes at most the configured number of reconnect attempts within one overall deadline, using the identical envelope. There is no durable transport queue, membership inference or automatic voter promotion. `stats()` exposes accepted packet counts, losses, saturation, opened connections, reserved cache slots and inflight calls without logging payloads.

The per-peer limit is currently one or two calls, matching the protocol's two reserved replication streams. It is an internal admission bound, not a throughput qualification or recommended cluster size. Further concurrency changes must coordinate transport stream reservations and node memory budgets.

Loopback tests exercise node-role mutual TLS, cached connection reuse, reconnect with identical request bytes, stale/conflicting route revisions, active-route removal and immediate rejection at the inflight bound. Frame encoding first computes and checks serialized size, so small Raft packets allocate their encoded size rather than the maximum negotiated frame capacity.

Node discovery uses a normal `QuicRemote` request carrying `Operation::PeerControl`; it is separate from the Raft-only connection pool. Wire authentication admits only `PeerRole::Node`, checks the tenant grant, nonzero group and a 64-byte selector cap. The control host enforces read-only decoding and quorum barriers. Existing Runtime-only `Operation::Control` authority is unchanged.

A listener that also serves enrollment (`QuicServer::bind_serving` with the enrollment ALPN) names each connection by the protocol its handshake negotiated (`net/directory.rs`). A connection on the data protocol (`focal/2`) names the certificate it presented through a live `PeerRegistry` grant, and one without a certificate, or whose certificate no grant names, names no peer and is refused before any request is read; each request is still checked against the grant current when it is dispatched. A connection on the enrollment protocol is a joiner, whose role lets it send the enrollment kinds and nothing else (`net/classes.rs`), so optional client authentication on the enrollment protocol never authorizes data traffic. Ordinary `server_tls` still requires mutual TLS. Loopback regressions deliberately use optional TLS client authentication and an enrollment ALPN to verify both paths reject before handler dispatch. A peer of the first data protocol (`focal/1`, focal's frames on QUIC streams of their own) shares no protocol with `focal/2` and is refused at the handshake.
