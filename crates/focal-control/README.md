# Durable metadata owners

`focal-control` hosts `focal-directory` and `focal-enrollment` on the disk-durable Raft implementation in `focal-consensus`. One root group owns region/delegation metadata and the public enrollment registry. Each directory partition uses a separate group. Several groups can use `open_on_wal` with the same node-owned `SharedWal`; their ordering and authority remain independent. The root contains no session table.

## Host interface

Create `ControlOptions::new(NodeConfig)`, a `ControlBootstrap::Root` or `::Partition`, and a node memory budget. Open a replica with `ControlReplica::open` or `open_on_wal`. Bootstrap includes the public enrollment CA; retain that exact bootstrap durably outside the application log so its canonical genesis hash can be checked on every reopen. Private signing keys and invitation secrets never enter control commands or checkpoints.

Call `drain(&AuthorityVerifier)` to recover before serving. Drive `campaign`, `tick`, peer `step_authenticated`, and subsequent `drain` calls through the node runtime. Before explicit authority activation, the supplied verifier must use pinned, authenticated evidence for infrastructure enrollment and session-log/replica-custody fences; verification must be repeatable during follower replay. After activation, proof-bearing directory commands use only the installed authority and public enrollment state; legacy directory commands are rejected and the supplied verifier cannot bypass that boundary. Peer transport must bind cluster, group, and node identity. `step` is an explicitly trusted in-process adapter used by tests.

`submit(ControlRequest, &verifier)` accepts at most one prepared mutation per group. It checks exact scope, client order, command size, root/partition revisions and delegation epochs, verifies command authority, and reserves the next directory/enrollment and retry state before proposing. New leaders cannot admit work until they have published a current-term committed prefix. This prevents an old retained proposal from racing fresh preparation against an outdated state.

`ControlSubmission::Pending` means admission only. `ControlEvents::completed` is released after durable quorum commitment and state publication. The exact locally prepared bytes publish without decoding, signature verification, or another memory reservation. That guarantee covers prepared metadata publication; Raft/WAL persistence and emitted events still require bounded staging reservations. Ordinary pressure leaves completion capacity available. Exhausting the total budget can fail-stop a drain; release pressure and reopen to determine the exact durable outcome. Followers and recovery reserve capacity before rebuilding committed state. Any persistence or committed-apply failure fail-stops the owner; reopen and replay before continuing. If leadership or snapshot replacement invalidates a local preparation, `uncertain` reports its ID. Its outcome is unknown until queried or retried with that same ID.

`root`, `enrollment`, and `partition` expose local state after successful drain. These getters grant no linearizable-read authority. Submit a `read_index` context, deliver messages, and wait for that context in `ControlEvents::read_states`; all returned barriers are at or behind the published prefix. A host must stop serving on drain failure. Immutable previously committed retry receipts can be returned from followers without reexecuting the operation.

For enrollment, prepare an invitation or join command with the registry and private `BootstrapAuthority`, submit it as `ControlCommand::Enrollment`, then release the invitation or certificate only after its control receipt commits. The registry's prepared-state adapter verifies certificates/CSR and reserves its complete next state before proposal; publication binds its applied index to the actual Raft index. Enrollment authorizes identity, not voter membership.

## Asynchronous replica service

`focal_node::control_host::ControlHost` supplies the owned runtime for either kind of metadata replica. `spawn(replica, verifier, config, budget)` returns a cheap clonable request handle, a joinable owner thread, and a bounded receiver of `ControlReplicationFrame`. The owner alone holds the replica and verifier. Separate bounded operator and peer queues keep an overloaded operator from consuming the peer queue. A full outbound queue drops the packet and increments `ControlProgress::dropped_replication`; Raft retransmits. `PeerAccepted` acknowledges only ingress, never a control mutation or quorum commitment. Frame memory reservations remain attached until the transport drops the whole frame.

The handle implements `focal_wire::RequestHandler`, so `QuicServer::serve(host)` uses the same bounded mTLS framing as session owners. Use `ControlHost::wire_limits()` for the 10 MiB frame ceiling that accommodates bounded metadata snapshots. Install authenticated peer routes in a `PeerConnectionPool` and drain the returned receiver with bounded concurrent sends. Transport routes grant reachability only: incoming Raft packets must match the dedicated metadata namespace, configured group, certificate-derived node ID, current voter or learner membership, and encoded Raft sender. Application handlers and transport registries remain deployment composition; this module does not enroll endpoints or change membership automatically.

`Operation::Control { group, request }` carries a bounded `ControlRpc`, and `Response::Control` carries `ControlReply`. Existing wire tags remain unchanged. A server-granted Runtime peer can submit or read metadata through that operation. The host binds `ControlRequest.id.client` to its authenticated principal and rejects requests crossing the configured metadata session, group, or route epoch. Local `submit` and `read` helpers run through the same verification boundary. The `AuthenticatedPeer` parameter is trusted server-owned input, never a deserialized caller claim. Directory evidence requires the installed authority verifier after activation (the injected verifier remains only for legacy groups). Runtime permission does not make an unverified fence valid.

`Operation::PeerControl { group, request }` provides node-only discovery without granting Runtime or actor authority. Its selector is capped at 64 bytes; the host rejects the `Submit` discriminator before decoding any command arrays. Enrolled nodes need the metadata tenant grant and exact namespace/group/route, but need not already be a voter to discover bootstrap state. The local `read` helper chooses this operation for a Node principal. Discovery occupies the bounded ordinary request lane, preserving Raft's separate ingress capacity. Node receipt queries retain the same own-principal restriction.

New writes await durable publication. Previously committed exact receipts can return on any recovered replica. `ControlRead::State` exports one bounded group checkpoint, and `Receipt` reads only the calling principal's receipt. `ControlRead::Membership` returns an owned `ControlMembership` containing node, leader, term, voters, learners and the published applied index. These selectors and `ControlRead::Authority` require a matching quorum ReadIndex in the current leader term before export; a current memory snapshot alone does not establish authority. Export memory is reserved after the barrier, using the current committed state size. Each pending waiter retains its input reservation. Accounted responses carry both input and exported-state reservations through network delivery or cancellation; the legacy direct `handle` method explicitly transfers budgeting to its caller. Host deadlines, lost leadership, or cancellation release waiters; timed-out Raft read contexts remain bounded by the consensus in-flight limit until quorum progress or term reset. A lost write waiter must retry the identical serialized `ControlRequest`, including its sequence and acknowledgment floor.

`stop` drains durable work and checkpoints only a fully delivered prefix without a pending preparation. Joining the returned owner confirms thread termination. Owner failures stop admission and complete remaining write waiters as unknown; callers must reopen and recover before serving again. `ControlProgress` exposes local identity, term, leader, published index, and metadata revisions for supervision, but grants no linearizable read authority.

## Explicit installed authority activation

Existing bootstrap material, genesis hashes, command ordinals, receipt fields and preactivation checkpoints retain their original encoding. `ActivateAuthority` is appended to the command enum: root activation compares the exact root/enrollment revisions and commits the initial authority clock in the existing root Raft group. Activation becomes visible only after quorum commitment. The root anchor derives from that group's actual identity and public enrollment CA. `Authority` then applies bounded `AuthorityCommand` mutations against the exact current enrollment revision and recorded time; node topology grants additionally require an existing root region with the matching authority epoch.

A trusted Runtime operator obtains `ControlRead::Authority` from the root through the host's matching ReadIndex barrier. It then commits `ActivateAuthority::Partition` in a destination partition. The snapshot pins the source cluster/group/genesis, public CA, exact authority/enrollment revisions and applied indexes. `InstallAuthority` subsequently replaces that snapshot only under its expected prior source index, unchanged anchor and source identity, strictly newer source index, nondecreasing state revisions, and nondecreasing recorded destination time. An unchanged revision requires identical state. Installation is the trusted authenticated owner's decision: serialized snapshot bytes alone are not a quorum certificate. Node-only discovery remains read-only and cannot submit activation, installation or grants. Root and partition groups have separate Raft indexes; an imported root index is never compared to the partition's local log position.

After activation, `VerifiedRoot` and `VerifiedPartition` carry `ControlEvidence` with exact installed authority/enrollment revisions, recorded decision time and bounded signed statements. The directory verifier borrows only the installed public state. It checks complete topology grants, current certificate revocation, generation, scope and proof expiry; external `AuthorityVerifier` callbacks are never invoked. Legacy `Root` and `Partition` mutations are rejected after activation. Enrollment mutations remain in the same root owner, so later root verification sees revocation immediately. A partition sees a revocation after a newer root snapshot is committed locally; automatic distribution and a global freshness/availability policy are not implemented.

Activated checkpoints use explicit schema 2, containing the legacy metadata/retry state plus installed authority, its original source, public enrollment snapshot and recorded time. Recovery also accepts unchanged schema 1 for legacy groups, and an activated live owner refuses a snapshot that would remove activation. Root recovery requires the authority export's enrollment bytes to match the root machine's enrollment state. Neither private keys nor invitation secrets enter this format.

Both the command size limit and authority/enrollment limits apply to installation. A root snapshot larger than the destination's configured command limit is rejected; there is no unbounded or hidden chunking path. This integration supplies durable verification and installation, not automatic placement, voter promotion, or producers for session/custody/delegation statements. Those producers must attest actual committed records and durable custody before the existing proof APIs can accept their results.

## Committed membership and node contacts

`ControlRead::Configuration` returns the exact canonical Raft member sets and the last applied configuration index after the host's ReadIndex barrier. Keep that index and configuration in `ControlMembershipCommand`, and submit `ControlCommand::Membership` with the usual authenticated Runtime principal and consecutive request identity. The command supports learner admission, promotion, removal, and leaving an existing joint configuration. Promotion checks the leader's durable replication progress through its commit index; adding a learner alone grants no vote. A normal application entry cannot execute a membership command.

The complete control envelope is carried in the real `ConfChangeV2.context`. Its one committed configuration entry applies the new Raft configuration and the existing bounded retry receipt together. Both ordinary and configuration events are processed in index order. Exact receipt retries return the original outcome even after leadership changes; changing intent under that ID conflicts. A new request compares the exact last-configuration index, preventing an old configuration from matching after removal and re-addition. Locally prepared before/after configurations must match the actual applied result before a receipt is released.

`ControlRpc::Transfer` / `ControlHost::transfer` require Runtime authorization and exact configuration/index preconditions. `TransferInitiated` acknowledges initiation only. Callers observe the target's later quorum-read result to establish leadership; transfer has no durable membership receipt and is not represented as a configuration mutation. Node-only `PeerControl` still rejects every non-read discriminator before decoding command payloads.

`Operation::NodeContact` is a separate bounded Node-only path. The host derives node ID, principal and certificate fingerprint from authenticated TLS, rechecks active committed enrollment even for a cached receipt, and supplies recorded decision time. Only address, expected generation and request sequence come from the peer. Generic Runtime submission of a contact command is rejected. `ControlRead::Contacts` returns a committed root contact snapshot, including an explicit empty snapshot before the first announcement. Contacts establish reachability only; they grant no topology labels, custody, Runtime permission or Raft membership. Route consumers must recheck enrollment revocation before using historical rows.

The first membership or contact mutation selects checkpoint schema 3: unchanged metadata/retry fields, optional installed authority, last configuration index and optional bounded contacts. Readers retain support for schema 1 and 2; existing bootstrap bytes, genesis hashes, command ordinals and receipt fields remain unchanged. Contacts preserve exact client intent across owner-clock changes on retry; only this new command's hash excludes its server-derived `decided_at`, while the full recorded envelope still includes time for deterministic replay.

These APIs are usable owner/transport components. An automatic invite-to-learner-to-voter service, route refresh orchestration and deployment CLI are not implemented here. Callers must retain the exact original bootstrap membership when opening a new replica with `NodeConfig::joining`, supply authenticated routes, and observe committed admission and catch-up before promotion.

## Exact bounded retries

A request ID is `(authenticated client ID, consecutive sequence)`. Each client has a configured bounded outcome window and a durable acknowledged floor. `acknowledged_through` on a new request drops only outcomes the client explicitly acknowledges. A retry with identical canonical request bytes returns the original receipt, including original Raft term/index and directory/enrollment revisions. Changing the payload under a retained ID returns `RetryConflict`. IDs at or below the floor return `RetryExpired`; they never execute again.

Unacknowledged outcomes are never silently evicted. A full window rejects admission until the next request acknowledges older results. Client slots are bounded for the lifetime of the group; automatic retirement/recycling of client identities is not implemented. The host must bind the client ID to the authenticated caller and durably retain its next sequence and outstanding request. A new random ID after an unknown outcome is unsafe.

## Recovery and limits

`checkpoint` captures the exact delivered prefix, complete public metadata state, and retry windows. Raft persists it and retains the suffix through the shared WAL generation machinery. Recovery validates schema, cluster/group/scope/genesis, metadata structural invariants, and receipt prefix bounds before publication. Snapshot transfer lets a lagging replica install the same metadata and retry floors. Enrollment checkpoint decoding additionally verifies issued certificate records and indexes.

Commands and snapshots have bounded encoded sizes; directory partitions, enrollment registries, retry clients, and retained outcomes have independent limits. Payload/frame decoding, cloned metadata, index overhead, and enrollment state use conservative memory reservations. Raft's retained entry/snapshot buffers and operation staging now share the supplied budget hierarchy, and the standalone constructor also charges its shared WAL to that budget. The `open_on_wal` constructor uses the supplied physical WAL's node-wide budget. `ControlEvents::take_allocation` transfers the consensus output permit when a host moves raw buffers into another owner; hosts that encode separately reserved frames retain the original permit until encoding finishes. Initial metadata preparation clones a bounded owner and retry table. Incremental metadata trees, background rebalance/split execution, automatic membership reconciliation, operator deployment orchestration, and fleet-scale benchmarks remain separate work.

The membership test uses four actual disk-backed replicas to verify no minority acknowledgment, learner snapshot catch-up before promotion, exact receipt/conflicting-intent handling, replacement leadership, stale-index rejection and checkpoint restart. Node host tests additionally exercise Runtime-only authorization and leader transfer. Contact tests cover both checkpoint and uncheckpointed WAL replay, server-clock-independent retry, certificate revocation and real QUIC announcements.

The authority integration test runs independent three-voter root and partition groups, drops an activation proposal's replication packets, elects a replacement leader, retries the exact request, and checks topology forgery, revocation, stale installation, unchanged legacy bytes/genesis, checkpoint recovery and WAL replay. Its injected verifier panics if invoked, ensuring installed authority cannot accidentally delegate verification to the caller.

Other tests run actual disk-backed Raft for one and three voters: publication under ordinary-memory pressure with reserved persistence capacity, total-budget exhaustion without partial publication, exact retries after checkpoint plus suffix replay, enrollment commit/revoke, all three WAL fault points, wrong genesis, independent groups sharing one physical WAL, minority isolation and leader replacement, and lagging snapshot catch-up. Run `cargo test -p focal-control --offline` and `cargo clippy -p focal-control --all-targets --offline -- -D warnings`.

The node `control_host` integration test runs three independently owned replicas through minority isolation, replacement leadership, exact request retry, and disk restart for root enrollment and a separate directory partition. Enrollment uses genuine CA/CSR verification and a complete TLS handshake before invitation disclosure. The `control_quic` integration test adds three real mutually authenticated QUIC services, operator RPCs, peer replication, route isolation, majority retry, and forged-principal/cross-namespace rejection. Run `cargo test -p focal-node --test control_host --test control_quic --offline`; the latter requires permission to bind local UDP sockets.
