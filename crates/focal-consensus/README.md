# Durable consensus ownership

`DurableNode::open_on_wal_in(config, shared_wal, &parent_budget)` places retained Raft entries, snapshot data, membership/progress bookkeeping, pending reads, outbound messages, and mutation staging under the supplied hierarchy. `is_budgeted_within` lets a host enforce ancestry before accepting a group. The physical shared WAL belongs to the node; it need not descend from an individual tenant. `open_in` also creates the physical WAL within the supplied budget. Compatibility constructors create independent budgets.

A group has an internal 512MiB allowance with 128MiB reserved for completion. These are ceilings, not preallocated buffers: a quiet single-voter group uses roughly 12KiB of accounted consensus state. The narrowest ancestor still controls admission. `propose` uses ordinary admission; trusted hosts use `propose_in(data, lane)` for completion commands. Ready persistence, peer processing, and committed application output use the completion lane. Application limits and checkpoint policy must bound retained history; this component does not autonomously checkpoint the application.

The Raft owner mutates alone. Before entering the dependency, it reserves conservative headroom for retained-log reads, message fanout, unstable entries, Ready, encoding, and emitted output. Retained payloads and vector capacities carry owned permits. Storage prepares and reserves its replacement entries/snapshot before writing any Ready records; only a successful WAL durability fence publishes the prepared storage. Snapshot compaction releases retained entry payload charges. The shared WAL has one disk writer; a shared owner can enqueue Ready batches for several groups and let them share one covering durability fence.

`try_drain()` returns `None` while it retains a Ready or LightReady, its prepared RAM state, accumulated output, WAL receipt, and operation permit. Each call queues at most one new WAL batch before yielding. `Some(NodeEvents)` releases the complete durable prefix. `persistence_pending()` gates all Raft mutation: step, tick, proposal, read-index, membership change, leadership transfer, and checkpoint return retryable `PersistencePending` until the owner polls the receipt. Hosts retain or requeue their input before calling an owned-input method; this crate does not maintain a second unbounded ingress queue. The pinned upstream `RawNode::ready` contract explicitly forbids mutation before `advance`; the gate is per group, so other groups continue. `drain()` waits on the same state machine's exact receipts without spinning. Hosts using nonblocking polling must schedule prompt follow-up polls while persistence is outstanding.

Initial Ready persistence installs prepared storage before advancing Raft. A LightReady commit increase queues a second hard-state write. No messages, read barriers, application entries, published applied index, or current-term authority are released until that additional fence is acknowledged. Failures discard the held output and stop the group; dropping the owner releases its RAM but cannot cancel a physical write already admitted to the shared WAL. Reopening resolves the durable prefix. The outstanding Ready uses one owned `Box` covered by its staging reservation, keeping idle replica objects small; it has no reference-counted payload ownership.

`NodeEvents` owns its output permit. A host moving fields into another queue must move `take_allocation()` alongside them, or keep it alive until independently accounted encoding completes. The permit can outlive the Raft owner and remains charged to every ancestor. No shared pointer wraps a Raft entry, snapshot, or event; the budget's shared atomic counters are the only cross-thread accounting ownership used here.

`MembershipConfiguration` is a canonical, bounded view of all four Raft member sets and joint-consensus mode. `propose_membership(expected, change, context)` compares that exact configuration, requires a published current-term prefix, refuses concurrent changes, and permits only learner admission, caught-up learner promotion, one-member removal, or leaving an existing joint configuration. Removing the final voter is rejected. It returns admission only. Durable `NodeEvents::membership` records carry the actual configuration entry index/term, opaque caller context, and exact before/after configurations. Applications merge these with ordinary entries by Raft index and persist their retry fences in their own checkpoints; consensus does not assign application request identities.

`NodeConfig::joining` takes the original group's exact bootstrap voters/learners while permitting a new local physical ID outside those sets. The replica has no voting weight until a committed promotion. Manual campaign on an unapplied or learner node returns a typed error before calling upstream Raft, which otherwise permits a manual campaign that can reach an absent-progress assertion. Leadership transfer accepts only another current voter and means initiation, not an election or durable configuration receipt. Existing bootstrap serialization and application snapshot bytes are unchanged.

Recovery preflights bootstrap vector lengths and snapshot membership before allocating. Protobuf peer preflight counts repeated entry structures and snapshot membership independently of bulk payload bytes; an 8MiB payload does not require a 256-times scratch reservation. Malformed length/varint and unsupported protobuf group encodings return typed errors. Supported entry and snapshot maxima are exercised through disk restart.

Completion reserve protects progress from ordinary pressure. It cannot guarantee progress after every byte of the total allowance is occupied: a drain that cannot reserve safe staging fail-stops without returning success or partially assembled events. Release pressure and reopen; Raft replay determines the durable outcome. Application metadata may publish a prebuilt state without another reservation, but the entire Raft/WAL path is not allocation-free. Reservations bound the concrete retained buffers and conservative dependency staging, not allocator-internal bookkeeping, thread stacks, or process RSS. Unexpected dependency unwinds are contained at the owner boundary; panic-abort and allocator abort remain outside that boundary.

Tests queue twelve real groups from one owner behind a bounded replay barrier and verify one covering flush, then separately test the LightReady fence, all three injected IO cuts, cancellation/restart, and retained staging/output accounting under group-budget pressure.

Run `cargo test -p focal-consensus --offline` and `cargo clippy -p focal-consensus --all-targets --offline -- -D warnings`.
